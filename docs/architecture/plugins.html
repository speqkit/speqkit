The official speqkit plugins

The kernel is a loader and everything else is a plugin. Which leaves exactly one question: which parts of "everything else" do we write and maintain, and which does the community write? The list is not here for completeness. It is here so that every plugin in the @speqkit scope has a reason to be there — and so that saying no is as well argued as saying yes.

The criterion

Ours is whatever decides how a test reads

A plugin is ours if it changes the way a test reads. A plugin is somebody else's if it connects one more system.

The file format, composition, generated data, the assertion vocabulary, control flow, the shape of a report, the surfaces — that is language. Two independent authors who each answer "how do I reuse a set of steps?" their own way produce two incompatible dialects and split the ecosystem in half. The very argument that fixes the spine inside the kernel works one floor up as well: the spine fixes the model, the official plugins fix the language.

Kafka, Mongo, Redis, Stripe, gRPC — one protocol, one vendor, one lifecycle each. A plugin like that can die and nothing breaks except itself. So it does not have to be ours — and should not be.

Ours — the language

  • the test format and its loading
  • composition: reusable blocks and actions
  • variables and generated data
  • the assertion vocabulary, schemas included
  • control flow
  • the reports CI reads
  • surfaces: CLI, TUI, editor

Not ours — systems

  • brokers, queues, buses
  • databases beyond the one we keep as a reference
  • clouds and object stores
  • SaaS with keys and billing
  • integrations with test management and chat
  • load testing, a11y, visual diffing
  • anything whose only reason to exist is one vendor
A closed list of exceptions — three

http, playwright, postgres are connectors and ours anyway. Each has its own reason, and the list is closed: if the exceptions ever reach five, there is no rule left.

http is not "one more system" — it is what nine tests in ten are about, and without it speq init means nothing. playwright and postgres each hold a piece of the contract nobody else exercises: a browser is the only honest consumer of resources and binary artifacts, and a transaction is the only honest proof that the test scope is real. They are ours as proofs of the architecture, not as integrations.

What being official costs

Every plugin in the scope is a commitment with no end date: a major of plugin-api means revising all of the official ones at once, and each of them becomes something people bring us bug reports about. Sixteen is the ceiling we can carry to 1.0, not a target. A plugin that does not pass the rule does not enter the scope even if it was written in one evening.

The ledger

What we publish

Three layers. Layer zero is not plugins at all — it is the tool itself. Layer one is the language: it is installed by default, and without any one of these nine there is some test that simply cannot be written. Layer two is official but on demand: nothing in it changes the language, and none of it loads until it is asked for.

Presets

A preset is an ordinary npm package with a speq.yaml inside it, listing plugins and default settings. One line pulls it in, and that is all there is to it:

# a service's .speq/speq.yaml, in full
version: 1
extends: "@speqkit/preset-api"

http:
  baseUrl: "http://localhost:8080"

None of the machinery has to be written — it is all there already. The extends chain is unrolled in packages/core/src/config.ts, the nearest file wins a conflict, a preset is installed like any other package and resolved from the store, and an environment layered on top of it cannot add a plugin — the very invariant that keeps --frozen honest. speq install even says so in its error: a preset is an ordinary package and it has to be fetched. So standing up our two means publishing two packages, not writing a subsystem.

Why we want them — four reasons

  • Thirty repositories. A platform team bumps the set in one place, instead of thirty services drifting into thirty different sets. That is what extends was in the spine for from day one.
  • It keeps the scope small. The pressure does not come from plugins, it comes from the sentence "let's just have it in the box". A preset absorbs it: "in the box" becomes the preset rather than the list of packages under @speqkit, and turning down a new official plugin stops meaning taking convenience away from anyone.
  • Onboarding. One line and a baseUrl in a service's config, instead of nine plugins with versions. speq init asks which preset and writes it itself.
  • It is the worked example. @acme/speqkit-preset is what we recommend to companies; our two are the first working demonstration of how that is done, rather than a privilege the kernel keeps for itself.

What is in them

PresetPluginsDefaults

What is deliberately not in them: postgres, allure and openapi. They are official, but each drags a decision behind it — a driver, a report format, a spec file — and a default preset has no business making decisions for a team.

A preset is policy; the lock is fact

A preset lists plugins and version ranges; the exact versions and hashes still live in the service's own speq.lock, and --frozen in CI installs those. Which is why a major of a preset is a deliberate change of set for everyone who pulled it in, and it has to be versioned like a public package rather than like an internal config.

The check

What a real suite actually asks for

A list derived from principles is worth exactly what its first meeting with reality shows it to be worth. That meeting was already arranged: food-cart-api, a Go service with Postgres, 32 migrations, a gate of 60 tests in 66 files, 20 JSON schemas, three action modules, two environments, and a workflow that parses summary.json. Plus food-cart-frontend: a guest menu on Next.js and a back office on Vite — a target for browser tests, where there are currently none.

The finding that matters is in the first line

The most frequent step in a real suite is not HTTP. use appears 179 times against api's 115: a suite of 60 tests rests on composition, of which we have not written a line. We wrote the browser, JUnit and the loop before the thing that is used more often than everything else put together. Which is where the order of work below comes from.

The second finding had to be corrected once it met the code. It read: not one of the fourteen rows needs a kernel change — the loader will lower a test into a single enclosing step, and cleanup will go into its finally. On paper it worked; in the executor it did not. A nested runSteps opens a child frame and pops it on the way out, so the bindings of the test's steps would live inside the wrapper while test-level assertions are read after it — and ${id.field} in them would silently cease to exist. Exactly the hole this project has already found four times: declared in the contract, does not work in practice.

Hence three additions to the kernel rather than none

It turned out that half of the Suite → Test → Step → Assertion model was simply not in the kernel. Assertions existed only on the test — and the corpus writes them on the step, 204 times. A test had a body and had neither setup nor cleanup — and the corpus writes them in 52 and 50 of its 60 tests.

Both belong to the kernel, and that is checkable rather than a matter of taste. A step type has no business reading an assert: block that is not its input: plugin-http with additionalProperties: false would reject it and would be right. And a plugin cannot express finally without dragging its child frame back into the caller, which is to say without breaking the invariant the frame exists for. Contract 0.6.0: StepDef.assert, TestDef.setup, TestDef.cleanup — three additions, PLUGIN_API_VERSION stays 1, and no ninth contribution point appeared.

The rule that decided it is worth writing down: what goes into the kernel is what a plugin cannot express without breaking an invariant. Everything else is a plugin, use included — it is expressible in full through that same re-entrancy.

Two questions nobody had asked got settled along the way. Cleanup runs after the test whatever happened to it — including after a setup that never finished, which is precisely when the rows a half-built test created stay in the database forever. And a test that answered its own question and could not clear up after itself is an error, not passed: the next run inherits what it left behind. Cleanup does not overrule a verdict already delivered — a failed test is the news.

A trap only a real corpus makes visible

variables have to be resolved once per test. A value provider is asked once per pass, and a pass is one step wide — make gen an ordinary provider and tenantSlug in setup, in the step and in cleanup becomes three different uuids, with the test registering one tenant, calling a second and cleaning up a third. Silently. Which is why gen is not only a provider: a test's values are computed once and live in the frame of the enclosing step.

The consequence

Two relocations inside what is already written

"Ours is the language" applies to what has been published too. Two places do not match it, and they are cheaper to move now, before the freeze, than after.

  • env → plugin-data moveddefineValueProvider('env') lived in plugin-http. An environment variable has nothing to do with HTTP: a project without a single HTTP step lost ${env:TOKEN}, and the plugin was answering for something it never promised. While we were there, an unset variable with no ${env:NAME:-fallback} is now an error rather than an empty string: Bearer  is a suite that fails for the wrong reason or, worse, passes against nothing.
  • assertions → plugin-assert movedjsonpath and body_contains check a value, not HTTP. Their twins will be wanted for a SQL row, a Kafka message body and the contents of a file — and every author will write their own if there is no vocabulary. What stays in plugin-http is what really is about the protocol: status and duration_under.

Both moves are majors of the plugins concerned and zero kernel edits. Compatibility is kept the ordinary way: the old assertion ids stay where they are, marked deprecated, until the next major.

The shape of a test

A test carries more than its steps

The v1 shape is decided, but its list of fields is not closed. link, owner, epic, severity, a ticket number — these are what a person opens a report for, not CI. There will be as many fields of that kind as there are teams, and they cannot be guessed in advance.

There is one rule: the kernel carries it and never reads it. It does not know what owner means, does not check it, and never looks at it when deciding what to do next. Everything outside the spine reaches the plugins as it was written — and from there it is their business.

Where a key counts as its own, and where as somebody else's

The difference between the levels matters more than it looks, and without it owner: on a step is either rejected by a schema or lost in silence.

  • testThe set of fields is closed by the spine — id, title, tags, variables, setup, steps, assert, cleanup. Everything else is metadata by default and goes into meta. Nothing has to be declared: write epic: menu and it is there.
  • step and assertionHere an unfamiliar field already belongs to the plugin that owns the type: — it is that plugin's input, not metadata. So on a step, metadata is written under a reserved meta:, and the kernel lifts it out before the schema is checked: otherwise plugin-http's additionalProperties: false rejects owner:, and is right to.
  • directorysuite.yaml makes the directory a suite: it hands metadata and tags to every test beneath it — an epic written once instead of in twelve files — and declares a setup and cleanup that run once around all of them. A test overrides what it inherited.

Where it ends up

  • Events — test.started carries the test's meta, step.started and step.finished carry the step's. That is where any reporter takes it from: Allure spreads it across labels, JUnit into properties, somebody's plugin into their own tracker.
  • The run log — since it is in the events it lands in the recorded log, and speq report redraws the report with the same metadata without re-running anything.
  • Validation — ValidateContext.test already exists, so a plugin sees the meta while it checks its own steps.
  • Execution — ${meta:owner} resolves like ${vars:…}, so an x-owner header is filled in without a single new line in the contract.
Validation belongs to whoever reads it

We do not validate meta and will not: we have no opinion about which fields are the right ones. A plugin that needs a field checks it itself at the moment it reads it, and complains with a diagnostic — the mechanism is already there and nothing has to be added. A typo in ownr costs a label missing from a report; a typo in a step type costs a check that silently never ran. Different price, different treatment.

Which is also why defineTestField does not appear: eight contribution points are eight contracts forever, and opening a ninth for the sake of annotations is a bad trade. In the contract this is four additions — meta on a test, a reserved meta on a step, a field on two events, and ${meta:…} — and not one new point.

The line past which meta becomes a problem

Meta describes a test; it does not steer one. The moment a plugin starts changing behaviour according to a meta field — retries: 3, skip: true, parallel: false — the suite has acquired control flow that validate cannot see, a report cannot explain and a user cannot find. If behaviour is wanted, it is a step type or a config key — something declared and checked. The kernel never branches on meta, and that is worth writing down as an invariant alongside the others.

The next thing grows out of the same field: --filter owner=… in the CLI. Tags are already filtered, owner and epic are the same family, and this is the CLI plugin rather than the kernel.

Depth

An official plugin is shallow by design

If our http does not suit you, you write your own, and that is a normal outcome rather than a failure. Hence the rule of depth: an official plugin covers what almost everyone does and stops where the specifics begin. http will not grow an OAuth flow, postgres will not run migrations, allure will not ship its own server. Not because it is hard, but because every step like that is somebody's particular case, paid for by our support forever — and it takes away an author's reason to write a plugin better than ours.

But today "write your own" runs into the preset

Two plugins cannot claim one step type — that is a kernel invariant. So to install your own http, ours has to come out. And there is nothing to take it out with: along an extends chain the plugin lists only add up (packages/core/src/config.ts:153), and config has no way to remove what arrived from a preset. While there were no presets this hurt nobody. With @speqkit/preset-api decided, it hurts everyone who uses it: extends plus your own http is a collision and a dead end whose only exit is abandoning the preset altogether.

So an exclusion goes into config alongside the presets: plugins: [-http, "@acme/plugin-http"], or a separate exclude. A small change, and in the kernel. Without it, "nobody is stopping you writing your own" is true only for people who do not use a preset — which is to say precisely not for the thirty repositories a preset exists for.

The boundary

What we do not write — and how it stays alive anyway

Saying no only works when the author has somewhere to go. Everything needed for that is already done: the contract is published, the scaffold generates a package, the kit runs it inside the real kernel, and the registry is ordinary npm. Nothing has to be agreed with us.

Rules of the common ground

  • The @speqkit scope is ours alone. The community publishes under its own name: speqkit-plugin-kafka or @acme/speqkit-plugin-kafka, plus the speqkit-plugin keyword, which is how a plugin is found in the registry.
  • awesome-speq is a list, not a seal of quality. Being on it promises a user nothing about support; it is a signpost, not a certificate.
  • Moving into the official set is an exception with four conditions at once: the plugin is about language rather than a system; we take on maintenance forever; conformance against test-kit is green; the author agrees to hand over the name. Miss any one of them and it stays a link in the list. That is how we avoid ending up with thirty plugins inherited out of kindness.
  • What we promise authors in return: a major of plugin-api with an announced date, migration notes, and a test-kit that breaks before their plugin breaks in someone's project.

The plan

The order the corpus dictates

Not one plugin at a time, but one criterion of done: the food-cart-api gate runs on the new framework and goes green. While it is red, every next plugin is a guess. The two decisions from the table above — meta in the contract and removing a plugin that came from a preset — are small and ride along: the first with step 4, the second with the presets at step 6.

  1. 1

    plugin-use done

    179 occurrences in the corpus. use by file and by action, modules with imports/alias, as for the result, returns out of an action, cleanup that runs after a failed test, and fixtures — the same call to something declared elsewhere, only handing back data.

    Underneath: use itself needed nothing from the kernel — ctx.runSteps with a child frame, exactly as expected. setup, cleanup and assertions on a step did need something: they cannot be expressed by a plugin without breaking that very frame. Contract 0.6.0, three additions, 12 new kernel tests.

  2. 2

    plugin-data done

    gen with uuid, string, int, email, date; env, relocated out of HTTP; and vars — a home for adminApi and tenantPassword, which in the corpus live in environments/*.yaml and would have been homeless in the new model. Fixtures went to use, and the plugin contributes no steps at all: it does nothing, it only answers.

    Underneath: the seed is the runId, which every reporter already prints and which already names the report directory — replaying a run's data means copying a string that is on screen. A value is derived from (seed, test name, generator, counter) rather than drawn from a shared stream, which is why a failed test re-run on its own sees exactly what it saw inside the suite.

    One more hole in the model: a test had no givens. Nobody could put a value in scope before the first step: a plugin's child frame is popped when its step returns. Contract 0.7.0 — TestDef.variables, resolved one at a time, in declaration order. That is not an implementation detail: ${...} asks a provider once per pass, deliberately, because a provider is a lookup rather than a generator. A block resolved in a single pass would have given slug and foreignSlug the same uuid, and the test that exists to prove two tenants do not overlap would have been checking one tenant against itself. As a side effect, a given can be written in terms of the one above it: email: "speq-${slug}@example.com".

  3. 3

    plugin-assert done

    Not only what is in the corpus. The corpus writes six kinds of check, but a team that has no word for "at least" or "is one of" writes a regex over a stringified body — and the suite stops saying what it checks. So the vocabulary is wide from the start: equality, order (greater_than, at_least, less_than, at_most), membership from both directions (contains and one_of — Python's in, but the direction is invisible in YAML, hence two words), text, presence, size, type and JSON Schema. jsonpath and body_contains moved in from plugin-http.

    Wide does not mean deep. A vocabulary is language, and language is our half of the line. There are no and/or/not combinators: a block already reads as "all of this is true", every check reports for itself, and a combinator would take that away. There are no custom comparators either: defineAssertion is a public contribution point, and a missing check is twenty lines in somebody else's plugin.

    Underneath: one selector for every check — a path into the whole step result, not into the body. The extra word body. is the price of the thing the plugin exists for: the same at_least reads a row out of SQL and the contents of a file. And schema goes through ajv rather than a subset of our own: a schema out of OpenAPI arrives with oneOf and $ref, and a validator that silently ignores keywords it does not know reports a check it never performed. A gate that lies is worse than a missing one. Schemas are compiled during validate — precisely the case 0.5.0 exists for.

  4. 4

    plugin-yaml grows up, and speq migrate appears done

    The loader understands the v1 shape and files everything unfamiliar into meta; init.yaml hands metadata to a directory and is not a test itself. The codemod translated the whole corpus: 66 files, 60 tests, zero diagnostics from speq validate. {{x}} → ${x}, type: api → type: http, $steps.a.response.body → ${a.body}, a folded bodyFromFixture → a use step, manifest.yaml with its environments → a speq.yaml with layers.

    What the codemod does not decide for you. suite.beforeEach has no successor yet, and the manifest's retry policy has no plugin. Anything like that is named by file, with what to do instead, and not carried across. A codemod that silently drops what it did not understand is worse than one that refuses: the suite still goes green, only the check that was guarding it is gone. Comments survive the rewrite — the document tree is rewritten, not the text — while the prose in them stays as it was: a comment explaining what callers write is something a codemod cannot rewrite correctly, and saying so is more honest than guessing.

    One change of meaning, and it is the point of the migration: a shared block now gets an owner at each call site. In v1 a block published its ids straight into the calling test — {{tenant.response.body.token}}, with nothing to say where tenant came from. A block runs in its own scope and hands its result back through the step that called it, so the codemod gives the step a name and rewrites the references through it. A leak became a record.

    Contract 0.8.0 — meta, exactly as decided: a test's spine is closed and the rest goes into meta; on a step and an assertion it goes under a reserved meta:, which the kernel lifts out before the schema is checked; fields on test.started and on both step events; ${meta:…} answers from the running test. No ninth contribution point appeared. A step's label is resolved — POST ${vars:adminApi}/tables in a report should be a request rather than a template — but it is not read: the kernel does not branch on meta, and a label that fails to resolve is shown as written and never fails the step.

  5. 5

    plugin-json, and multipart in http done

    reports/results/summary.json in the shape the current workflow parses — folded out of the event stream without a single look at the run result: which means speq report redraws it byte for byte, and a reporter that cannot be written from events alone is a hole in the events rather than a reason to give reporters a back door.

    The shape is somebody else's contract, and you can tell by the ugly part. totals.pending is the same number as totals.skipped. Nobody designs that on purpose, and that is exactly why it is there: a jq expression in another repository says .totals.pending // 0, so renaming the key would make that workflow report zero pending tests instead of failing. The report would be wrong and nothing would say so. The moment somebody parses a shape it stops being ours to tidy: keys get added, never renamed. In verify-publish the file is read by exactly the four paths that workflow names.

    Making that number mean something required pending to become real — and it is a field of the spine rather than an annotation: it changes what happens, so it is declared and checked. Contract 0.9.0 takes a reason, not a flag: a test parked without one is a test being deleted slowly, and the reason is the only thing that makes the entry worth keeping over git rm. A pending test is still validated — it is precisely the test nobody runs, and therefore the one that rots unnoticed.

    Multipart comes from the corpus's own "known gaps" section. It records that the upload paths have no test for a successful upload, and why: multipart, formData, form, files, bodyFile and bodyRaw were every one of them silently ignored, the request went out with an empty body, and the test reported passed. Three paths stood uncovered for months behind a green tick, and the note ends with "watch out for this generally: unknown step keys do not fail validation". Here they do: the schema is closed, an unknown key is a diagnostic before the first request goes out, and a part naming a file that is not on disk is found the same way, in milliseconds.

    Retrying is off by default, and two of the defaults are decisions. 429 is not on the list: a rate limiter is behaviour a suite checks, and a policy that quietly repeats through a 429 makes the test for the limiter pass whether the limiter exists or not. That is worse than having no test. And only idempotent methods repeat: a 502 means a gateway answered, not that the origin never saw the request — a repeated POST creates the row twice, and the suite fails on a duplicate key somewhere else entirely.

  6. 6

    The gate goes green — and only then presets and layer 2

    The 60 tests of food-cart-api pass on the new framework, with the workflow unchanged in meaning. After that: preset-api, preset-web, a browser suite for food-cart-frontend, which currently has no tests at all, and then postgres, openapi, allure.

    Underneath: the same move that worked twice on the M3 gate — a real consumer first, conclusions second. A corpus of 60 tests will find things in the language that no amount of reasoning about the language will.

The check produced the headline finding and one that was not obvious: the most frequent thing in a real suite is not HTTP but composition, of which we had none — and at the same time not one of the fourteen gaps it found requires a kernel change, so the corpus is no obstacle to freezing plugin-api at 1.0. There are exactly two kernel edits, both small and both consequences of what was decided: meta on a test (which arrived with step 4, contract 0.8.0) and the ability to remove a plugin that came from a preset. The second is the price of "write your own" being literally true.
