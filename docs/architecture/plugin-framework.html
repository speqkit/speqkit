Ядро — только загрузчик плагинов. HTTP, CLI, UI-тесты, отчёты, TUI и даже управляющие конструкции вроде цикла — всё это плагины. Новый продукт без монетизации — фреймворк для комьюнити тестировщиков от тестировщиков. speq-cli продолжает жить своим циклом, его v1.4 и v1.5 заморожены.

Контракт ядра

Хребет

«Всё — плагин» никогда не бывает буквальным: в VS Code точки вклада зашиты, в pytest неизменен цикл collect → fixture → runtest → report. Если тестовая модель тоже плагин, два пользователя одного фреймворка пишут несовместимые тесты. Поэтому хребет фиксируется и не меняется.

Что ядро содержит — исчерпывающий список

Plugin registry + lifecycle   загрузка, порядок, зависимости между плагинами
Config                        speq.yaml, extends, профили окружений
Test model                    Suite → Test → Step → Assertion, адресуемые id
Execution                     порядок, контекст, привязка результатов по id,
                              интерполяция ${...}, бюджет таймаутов,
                              реентрантный runSteps() — доступен плагинам
Resource lifecycle            объекты со сроком жизни run | suite | test
Event bus                     поток событий прогона, версионированный
Result + artifacts            модель исхода и вложений (включая бинарные)
Validation                    плагин отдаёт схему, ядро проверяет тест до запуска
Installer                     резолв версий, lock, кэш плагинов

Ядро не содержит: ни одного протокола, ни одной команды CLI, ни одного формата отчёта, ни одной управляющей конструкции, ни одного UI.

Восемь точек вклада — и больше в v1 не открывать

Каждая открытая точка становится контрактом навсегда: закрыть обратно нельзя. Восьми достаточно, чтобы написать http, playwright, postgres, loop, tui и vscode.

  • defineStepTypeid, схема входа, execute(ctx, input) → результат, привязываемый по id
  • defineAssertionid, вид цели, схема, evaluate(target, expected)
  • defineResourcescope run | suite | test, setup/teardown. Браузер, пул коннектов, транзакция
  • defineReporterподписка на шину событий → вывод в любом формате
  • defineValueProviderрезолверы ${...}: env, vault, faker, свои источники
  • defineLoaderкак находятся и парсятся файлы тестов. YAML — реализация по умолчанию
  • defineCommandвклад в CLI-поверхность через опциональную зависимость от сервиса cli
  • defineHookbefore/after на уровне run, suite, test, step — для трейсинга, скриншотов при падении, очистки
Опциональные зависимости — работает

Плагин postgres хочет добавить команду speq db:seed, но CLI может быть не загружен — в VS Code его нет. Плагин объявляет опциональную зависимость через ctx.inject(['cli'], …): команда регистрируется, только если сервис поднят, и плагин остаётся полностью работоспособным, если нет. Это шаблон inject из Cordis, реализованный за фасадом двухфазной загрузкой — оба случая закрыты тестами.

Обратное направление — ctx.host

Восемь точек выше — это то, что плагин даёт ядру. ctx.host — то, что он у ядра берёт: discover, validate, run, runs, replay, плюс корень проекта, каталог отчётов и текущее окружение. Этой стороны в контракте не было, и plugin-cli взял недостающее единственным доступным способом — import { bootstrap, runTests } from 'speqkit'. Плагин исполняется внутри уже поднятого ядра и не может привезти своё, поэтому на Host нет и не будет bootstrap: это текущая сессия, а не способ открыть вторую. Договариваются плагин и ядро по-прежнему об одном — о мажоре plugin-api, который проверяется как apiVersion. Никакой версии ядра плагину не нужно.

Поток событий

run.started → suite.started → test.started → step.started
  → step.finished → assertion.evaluated → artifact.attached
  → test.finished → suite.finished → run.finished
  ⊥ diagnostic

step.started несёт parentId → вложенные шаги рисуются деревом

На этом контракте стоят CLI, TUI, VS Code, будущий агрегатор и любой сторонний репортер — одинаково. Если сделать правильно только это, «много поверхностей» получается само.

Требование

Автор плагина не ограничен

Проверка требования на самом жёстком случае: не хватает цикла. Цикл — не тип шага в обычном смысле, он оборачивает другие шаги. Если это выражается плагином, выражается всё.

Что пишет автор

export default definePlugin({
  name: 'loop',
  setup(ctx) {
    ctx.defineStepType('loop', {
      schema: z.object({
        over:  z.string().optional(),    // ${users}
        times: z.number().optional(),
        as:    z.string().default('item'),
        steps: ctx.schema.steps           // дочерние шаги — тип из хребта
      }),
      async execute(ctx, input) {
        const items = input.over ? ctx.resolve(input.over) : range(input.times)
        const out = []
        for (const item of items) {
          out.push(await ctx.runSteps(input.steps, { vars: { [input.as]: item } }))
        }
        return { iterations: out.length, results: out }
      }
    })
  }
})

Что получает пользователь

steps:
  - id: seed
    type: loop              # из speqkit-plugin-loop
    over: ${users}
    as: user
    steps:
      - id: create
        type: http          # из plugin-http
        method: POST
        url: /users
        body: { name: "${user.name}" }

Чего это требует от хребта — и почему решение принять надо сейчас, а не потом:

  • steps — рекурсивный тип первого класса. Дочерние шаги парсит и валидирует ядро, а не плагин. Плагин получает их уже разобранными.
  • ctx.runSteps(steps, { vars }) — реентрантный исполнитель с дочерней областью переменных.
  • События вкладываются. parentId в step.started, иначе TUI и отчёты не нарисуют дерево.

Следствие: if, retry, parallel, try/catch, repeat-until, foreach-file — всё это плагины. В ядре нет ни одной управляющей конструкции, и добавлять их туда никогда не понадобится.

Открытый вопрос

Адресация результатов внутри вложенных шагов. ${seed.results[0].create.body.id} — рабочий, но громоздкий вариант; альтернатива — плоские алиасы, которые плагин объявляет сам. Решить до M1, потому что это часть публичного DSL.

Главный сценарий

От «хочу писать тесты» до зелёного CI

Микросервис payments-service на Go. Node в репозитории не появляется ни на одном шаге.

  1. 0

    Поставить фреймворк

    brew install speqkit       # или curl … | sh

    Под капотом: один исполняемый файл со встроенным рантаймом: 116 МБ на диске, 37 МБ в архиве. Умеет он ровно четыре вещи: прочитать конфиг, поставить плагины, поднять их, отдать им управление. Ставится speqkit, на PATH ложится speq — то же разделение, что у @angular/cli и ng, и по той же причине: имя проекта не обязано быть тем, что набирают пятьдесят раз в день.

    Рантайм внутри — конкретная версия Node, прибитая в scripts/build-binary.mjs и скачиваемая с nodejs.org под проверку SHASUMS256.txt. Не тот node, что оказался на сборочной машине: у пакетного менеджера он бывает 66-килобайтной обёрткой над общей библиотекой, внутрь которой нечего внедрять, — и версия рантайма у пользователей стала бы свойством сборочной машины вместо решения, записанного в диффе.

  2. 1

    Инициализировать в репозитории сервиса

    cd payments-service
speq init

? Режим …………… in-repo (тесты рядом с кодом)
? Пресет ………… @acme/speqkit-preset
? Плагины ……… http, cli  (+ из пресета: postgres, allure)
✔ создано .speq/ · speq.yaml · speq.lock · suites/health.yaml

    Под капотом: init живёт в загрузчике, а не в плагине — иначе его неоткуда было бы вызвать до установки плагинов.

  3. 2

    Подтянуть плагины

    speq install

  resolving 4 plugins …
  ✔ @speqkit/plugin-http        2.1.4   cached
  ✔ @speqkit/plugin-cli         2.1.0   downloaded
  ✔ @speqkit/plugin-postgres    1.3.2   downloaded
  ✔ @acme/speqkit-plugin-kafka  0.4.1   downloaded
  → speq.lock updated

    Под капотом: реестр — npm, установщик — свой. Плагины ложатся в ~/.speq/plugins/, а не в репозиторий. Коммитится только speq.lock с точными версиями и хешами.

  4. 3

    Написать тест

    # .speq/suites/checkout.yaml
name: checkout
steps:
  - id: login
    type: http
    method: POST
    url: /auth
  - id: order
    type: sql               # появился вместе с plugin-postgres
    query: "select status from orders where id = ${login.body.orderId}"
assert:
  - type: status
    expected: 200
  - type: row_equals
    path: status
    expected: PAID

    Под капотом: схемы плагинов уезжают в yaml-language-server, поэтому автодополнение type: sql и его полей появляется в редакторе само, без правок расширения.

  5. 4

    Проверить, ничего не запуская

    speq validate

  .speq/suites/checkout.yaml:8  unknown step type 'ui'
    ↳ не найден среди загруженных плагинов
    ↳ возможно: speq add @speqkit/plugin-playwright

    Под капотом: ядро собирает полную грамматику DSL из загруженных плагинов до первого сетевого вызова. Опечатка ловится за миллисекунды, а не в середине прогона.

  6. 5

    Прогнать локально

    speq run --env local
speq run --test suites/checkout.yaml
speq tui                     # если поставлен plugin-tui

    Под капотом: открываются ресурсы scope run (пул коннектов), на каждый тест — scope test (транзакция), после теста транзакция откатывается. Изоляция данных при параллельном прогоне получается из этой же модели.

  7. 6

    Понадобился ещё плагин

    speq add @speqkit/plugin-playwright
speq add github:acme/speqkit-plugin-legacy   # из git
speq plugins                              # что загружено и что вносит

    Под капотом: add правит speq.yaml, пересчитывает speq.lock и обновляет кэш. Приватный скоуп компании, git-URL и локальный путь работают одинаково — это всё умеет npm-резолв.

  8. 7

    Возможности не хватило — пишем свой плагин

    npm create speqkit-plugin loop     # скаффолд: src, схема, тесты, CI
cd speqkit-plugin-loop && npm run dev

cd ../payments-service
speq link ../speqkit-plugin-loop   # подключить без публикации
speq run                        # сразу видно в тестах

cd ../speqkit-plugin-loop
npx speq-test-kit               # конформанс: таймауты, error, артефакты
npm publish                     # → доступно всем

    Под капотом: speq link — единственное, что отличает разработку плагина от его использования. Публикация — обычный npm publish; ничего согласовывать с вами автору не нужно.

  9. 8

    Поставить в CI

    # .github/workflows/tests.yml
- uses: acme/setup-speq@v1
  with: { version: '2.1.0' }
- run: speq install --frozen        # строго по lock, как npm ci
- run: speq run --env ci --reporter console,junit

    Под капотом: --frozen падает, если speq.lock разошёлся с speq.yaml. Exit code — из хребта; репортеры — плагины. Побитовая воспроизводимость набора плагинов, чего у нынешнего brew install speq нет в принципе.

Раскладка

Файловая структура

Три разных репозитория, три разные раскладки. Локально — новый каталог рядом с текущим, ~/speqkit/; в нынешнем ~/speq/ ничего не трогаем.

А. Монорепа фреймворка

speqkit/                        # новая организация GitHub
├── packages/
│   ├── core/           speqkit              ядро + bin `speq`
│   ├── plugin-api/     @speqkit/plugin-api        только типы — публичный контракт
│   ├── installer/      @speqkit/installer         резолв, lock, кэш
│   ├── plugin-http/    @speqkit/plugin-http       смоук-набор из коробки
│   ├── plugin-cli/     @speqkit/plugin-cli        run · validate · list · report
│   ├── plugin-playwright/ @speqkit/plugin-playwright браузер, ресурсы, скриншоты
│   ├── plugin-tui/     @speqkit/plugin-tui
│   ├── create-plugin/  @speqkit/create-plugin     скаффолд для авторов
│   └── test-kit/       @speqkit/plugin-test-kit   конформанс-тесты
├── examples/                     эталонные проекты, e2e
├── docs/                         спека хребта, гайд автора плагина
├── pnpm-workspace.yaml
└── .changeset/                   версионирование пакетов

Монорепа — сознательный разворот относительно нынешнего speq. Мультирепа правильна для стабильного продукта и убийственна для нового: первый год plugin-api будет меняться постоянно, и нужны атомарные правки ядра и пяти плагинов одним коммитом. Сторонние плагины живут в своих репозиториях с первого дня.

Пресет организации решает проблему тридцати репозиториев

Без него через полгода в тридцати сервисах тридцать разных версий плагинов и никакой возможности обновить централизованно. Пресет — обычный npm-пакет во внутреннем скоупе: платформенная команда бампает его, обновляются все сервисы. Это же естественная точка, где компания навязывает стандарты — обязательные репортеры, аллоулист плагинов, общие фикстуры. extends надо заложить в хребет сразу: прикручивать его потом к плоскому конфигу больно.

Поверхность

Команды

Разделение принципиальное: загрузчик владеет тем, что должно работать до того, как плагины подняты. Всё остальное приходит из плагинов — и если plugin-cli не подключён, этих команд просто нет.

Загрузчик — speqkit

Контракт

Версионирование и совместимость

Версионируются независимо три вещи. Путаница между ними — самая частая причина, по которой плагинные экосистемы становятся неподдерживаемыми.

ЧтоПравилоКто ломает
@speqkit/plugin-apiСтрогий semver. Минор — только добавление, мажор — разрешённый сломВы, редко и осознанно
speqkitСвоя версия. Может расти мажорами, не трогая плагины, пока plugin-api тот жеВы, свободно
Каждый плагинСвоя версия. Объявляет peerDependencies: @speqkit/plugin-apiЕго автор
DSLversion: 1 в speq.yaml. Миграции с внятным сообщениемВы, на мажорах
Схема событийВерсионируется отдельно — на ней стоят внешние потребителиВы, аддитивно

Правила совместимости

  • Плагин совместим с ядром тогда и только тогда, когда совпадает мажор plugin-api.
  • Ядро сверяет это при загрузке и отказывается грузить несовместимый плагин с внятным сообщением — а не падает в середине прогона.
  • Ядро поддерживает N−1 мажор plugin-api минимум 12 месяцев. Без окна депрекации серьёзные авторы плагинов вкладываться не будут.
  • speq.lock хранит точные версии и хеши; --frozen в CI даёт побитовую воспроизводимость.
  • Пресет организации пиннит версии для всех сервисов сразу.
Обещание стабильности — объявить вслух

0.x — ломаем что угодно и без предупреждения. 1.0 — plugin-api заморожен на мажор. Пока этой строчки нет в README, экосистемы не будет: никто не станет писать плагин против контракта, который может исчезнуть.

Требует решения

Открытые вопросы

Осталось три: первый закрыт. Два прежних и один, который нашёл гейт. Два снятых остаются снятыми: монетизации не будет, v1.4 / v1.5 заморожены.

  1. Название — решено. Проект называется speqkit, команда в терминале — speq. Скоуп @speqkit в npm и организация github.com/speqkit заняты нами. Так вышло не от хорошей жизни: из девяноста проверенных кандидатов ни одно словарное английское слово в npm не свободно, а speq занят заброшенным placeholder'ом 0.0.0 и живым чужим @speq-ai/speq. Разделение имени пакета и имени бинарника — обычная практика (@angular/cli даёт ng), и оно даёт чистое пространство имён на всех четырёх осях при четырёх символах под пальцами. Ядро публикуется как speqkit без скоупа, чтобы строка установки читалась npm i -g speqkit, а не как установка чужих потрохов; скоуп @speqkit остаётся за плагинами и контрактом. Имя команды вообще не является ничьим пространством имён, и отнимать его не у кого.
  2. Адресация результатов внутри вложенных шагов. Сейчас работает ${seed.results[0][0].body.id} — точно, но громоздко. Альтернатива: плагин объявляет плоский алиас сам. Часть публичного DSL, поэтому до 1.0.
  3. Скриншот при падении: что видит хук. Найдено гейтом, а не придумано. HookPayload в test:after не несёт ни исхода теста, ни attach — плагин физически не может узнать, что тест упал, и приложить снимок, доказывающий это. Два пути: либо хук получает исход и возможность приложить артефакт, либо перехват падения становится шагом — try/catch как тип шага, ровно тем же приёмом, что и loop. Второй честнее по отношению к принципу «управление потоком — это плагин», но требует, чтобы шаг мог поймать падение соседнего. Часть публичного контракта, поэтому до 1.0.
  4. Cordis — внутрь фасада или нет. Реестр реализован своими ~170 строками за интерфейсом PluginContext; сервисы и опциональная инъекция уже работают. Замена внутренностей на Cordis — правка одного файла, plugin-api её не увидит. M2 прошёл, и потребности в HMR так и не возникло: решение снова отложено, теперь до заморозки 1.0. Фасад ровно для того и делался, чтобы откладывание ничего не стоило.
План

Вехи

  1. M0

    Прототип хребта · сделано

    Ядро с реестром type, два фиктивных плагина, один YAML-тест. Цель — увидеть, держит ли хребет, до решений по названию и заморозке roadmap.

  2. M1

    Хребет стоит · сделано

    core + plugin-api + plugin-yaml + plugin-http + plugin-cli + plugin-loop. YAML-тест проходит end-to-end против реального API; в ядре нет ни одного упоминания HTTP. 12 архитектурных тестов зелёные, типизация чистая.

  3. M2

    Установщик · сделано

    Главный технический риск оказался ровно там, где ожидался, и в основном взят. speq install ходит в npm-реестр по HTTP сам: резолвит диапазон, качает tarball, сверяет sha512, распаковывает, раскладывает стор и пишет speq.lock. Ни npm, ни pnpm, ни yarn не вызываются — требовать тот самый пакетный менеджер, который мы заменяем, значило бы отменить всю затею.

    Раскладка стора — pnpm'овская, и по pnpm'овской причине. Зависимость — это симлинк внутри каталога самого зависящего пакета, поэтому обычный резолв Node, который ходит по реальным путям, её находит, а два плагина могут хотеть разные версии одной библиотеки. Ссылки относительные, стор остаётся переносимым. Проверено вживую: chalk@^4.1.2 с шестью транзитивными зависимостями ставится и импортируется из стора.

    Пресеты задали форму установщику. extends называет npm-пакет — значит конфиг нельзя прочитать, пока этот пакет не на диске. Установщик принимает не два списка, а два колбэка, и сам делает проходы в правильном порядке.

    Работают --frozen (ставит строго по локу и падает на расхождении с speq.yaml), add/remove (правят speq.yaml через YAML-документ, комментарии выживают), link (побеждает и стор, и node_modules), doctor (говорит, какие плагины приехали из node_modules и потому не воспроизведутся в CI).

    Дорога до зелёного CI закрыта — и она нашла третью дыру того же рода, что дважды находил гейт. environments/ создавался с M0 и не читался никем: флага --env не существовало вовсе. Теперь окружение — это слой настроек поверх speq.yaml, и только настроек: добавить плагин оно не может, потому что набор плагинов фиксирует speq.lock, а speq install --frozen отрабатывает в CI раньше, чем кто-либо сказал, какое окружение возьмёт прогон. Окружение, умеющее втащить плагин, породило бы лок, верный для local и неполный на один пакет для ci. В конфигах раскрываются ${env:NAME} и ${env:NAME:-fallback}, а незаданная переменная — это ошибка, а не пустая строка: иначе набор молча целится в localhost и зеленеет против ничего. ${login.body.id} при этом не трогается — этот синтаксис принадлежит прогону.

    defineReporter лежал в контракте с первого коммита, и его не вызывал ни один плагин. Консольный вывод ходил напрямую в events.subscribe — мимо механизма, а не через него. Это ровно то же, что гейт нашёл в attach и в scope suite, и чинится так же: консоль стала обычным репортером и значением --reporter по умолчанию, чтобы механизм проходил самый частый путь. ReporterDef получил необязательный init(ctx) с runId, outputDir и runDir — репортер, пишущий файл, не мог узнать, куда писать. Необязательный метод, поэтому plugin-api 0.3.0, а PLUGIN_API_VERSION остаётся 1.

    Каждый прогон пишет свои события в events.jsonl, и speq report проигрывает их заново в ту же шину. Это не удобство, а способ проверить главное утверждение архитектуры. Если поток событий действительно тот контракт, на котором стоят репортеры, TUI и панель VS Code, то отчёт, собранный из записи, обязан совпасть с отчётом живого прогона. @speqkit/plugin-junit строит XML только из RunEvent, без доступа к результату раннера, а тест требует побайтового совпадения. В день, когда поток событий перестанет описывать прогон целиком, это выяснится там, а не в чужом плагине через полгода.

    Сборка и проверка публикации. Все тесты репозитория ходят в src через алиас сборщика — и ровно это спрятало, что exports указывали на TypeScript, а Node отказывается снимать типы внутри node_modules: опубликованный так пакет не загрузился бы вообще. Пакеты собираются проектными ссылками (tsc -b) в dist, а scripts/verify-publish.mjs не верит ничему: пакует настоящие тарболы, поднимает временный реестр по HTTP, ставит в одноразовый стор и запускает CLI из dist обычным node в каталоге, где нет ни одного node_modules. «Установщик проверен на чужих пакетах, но не на наших» — закрыто.

    Стенд нашёл четвёртую дыру того же рода, и на этот раз не гейт. plugin-cli объявлял speqkit обычной зависимостью — потому что контракт не давал плагину никакого способа дотянуться до работающего ядра. Цена оказалась двойной и совершенно тихой: установщик честно положил вторую копию ядра в стор и запинил её в speq.lock, а сам плагин звал bootstrap() внутри процесса, который уже загрузился. Два реестра, каждый плагин загружен дважды за вызов, и отвечает не то ядро, которое поставил пользователь, а то, которое пинит лок. Всё зелёное — и всё неверно. Починка та же, что и в трёх предыдущих случаях: недостающее направление добавлено в контракт, а не обойдено. Появился ctx.host, plugin-cli не импортирует ядро ни строкой, и его package.json называет только plugin-api в peer. Инвариант закреплён с двух сторон: тест падает, если манифест любого плагина упоминает ядро, стенд падает, если ядро вообще оказалось в сторе. Только добавления, поэтому plugin-api 0.4.0, а PLUGIN_API_VERSION остаётся 1.

    Шаг 0 закрыт. scripts/build-binary.mjs собирает единственный исполняемый файл: ядро, установщик и yaml бандлятся в один CommonJS, Node SEA кладёт его блобом внутрь официального рантайма, postject внедряет, macOS переподписывает. Плагины внутрь не попадают намеренно — они по-прежнему грузятся в рантайме по абсолютному пути из ~/.speq, и import() из блоба достаёт настоящую файловую систему. Бинарник с вшитыми плагинами был бы другим продуктом — ровно тем, ради отсутствия которого всё это писалось.

    Доказательство не отдельное, а то же самое: verify-publish.mjs получил флаг --binary и гоняет по исполняемому файлу ту же батарею, что по опубликованным пакетам, с PATH=''. Установка из временного реестра, шесть пакетов в стор, четыре плагина оттуда, прогон набора, --frozen при недоступном реестре — всё это там, где node недостижим в принципе. Два способа доставки, одно определение слова «работает». Старт — 30 мс: блоб несёт V8-кэш, поэтому и собирается тем же рантаймом, в который внедряется.

    Доставка: packaging/install.sh (curl … | sh, sha256 сверяется, при расхождении не ставится ничего), packaging/homebrew/speqkit.rb и scripts/render-formula.mjs, который отказывается рендерить формулу, если в релизе не хватает хотя бы одной из четырёх платформ: тап, верный на трёх и молча отсутствующий на четвёртой, хуже, чем никакого тапа. release.yml собирает darwin/linux × arm64/x64 на родных раннерах — кросс-компиляция невозможна из-за того же V8-кэша и из-за того, что переподписывать Mach-O умеет только macOS.

    Подпись под macOS — ad-hoc, и это конечное состояние, а не незакрытый пункт. Нотаризация стоит аккаунта Apple Developer и сертификата в CI, а покупает ноль на обоих путях, которыми ставят на самом деле: brew снимает атрибут карантина сам, а у файла, скачанного через curl, его и не появляется. Gatekeeper останавливает только скачанное браузером — и ответ на это install-скрипт, а не сертификат. Решено: нотаризации не будет.

    Плагин теперь может приехать не из реестра. github:acme/plugin#v2, gitlab:, bitbucket:, git+ssh://…#main, git+file:// и тарбол по URL. Ref резолвится в коммит на установке, и в лок пишется только коммит: #main через месяц значит другое, а --frozen в CI обязан поставить то, что ревьюили. Коммит уходит в ключ стора как semver build metadata — 1.4.0+8f2c1ade9b7c, — потому что два коммита могут нести одинаковый version, а зависимость, просящая ^1.4.0, должна остаться удовлетворённой.

    Git-специи вызывают git — и это сознательное исключение из правила, которому подчинено всё остальное. Реестр мы обходим сами, потому что npm — это ровно тот инструмент, который заменяется; требовать его значило бы отменить затею. Git не заменяется ничем, он уже стоит у того, чей это репозиторий, и обращение к нему покупает три вещи, которых не даст никакой самописный HTTP: приватные репозитории работают через уже настроенные креды и ssh-агент, самохостед не требует диалекта API под каждого вендора, а коммит проверяет git, а не вендорский JSON. Нужен он только git-специям — больше нигде, включая standalone-бинарник.

    Сборка не запускается никогда. Отказ выполнять install-скрипты — это и есть то, что делает установку из репозитория защитимой, поэтому репозиторий без закоммиченного entry point отвергается на установке с объяснением, а не ставится чисто и падает через несколько минут внутри загрузчика плагинов, который не может сказать почему. Тарбол по URL хешируется на приёме, и хеш идёт в лок: реестра, который бы за него поручился, здесь нет. Токен реестра при этом не уходит на хост, который не реестр, — раньше уходил на любой, чей URL оказался в паке.

    Не сделано: из каналов доставки нет Docker-образа и setup-speq — и то и другое обёртки вокруг уже собранного артефакта, и живут они в отдельных репозиториях. Не читается .npmrc; приватный реестр работает через SPEQ_REGISTRY и NPM_TOKEN.

  4. M3

    Гейт · пройден

    plugin-loop прошёл первым: цикл и retry написаны против опубликованного API, ядро не менялось ни разу, вложенные шаги исполняются в дочернем скоупе. plugin-playwright добил вторую половину — ресурсы со scope и бинарные артефакты, те части хребта, которых цикл не касался. Живой Chromium, два теста, PNG 1280×720 доезжает до диска байт в байт.

    Ресурсы прошли без единой правки ядра. Три scope, ресурс, зависящий от ресурса (page → context → browser), конфиг доезжает до setup, teardown в обратном порядке даже когда тест падает, ассерт достаёт page сам — без шага перед ним. Один браузер на весь прогон: второй тест открывает страницу за 222 мс против 2463 мс у первого.

    Артефакты не прошли — но это оказалась не ошибка хребта, а невыполненное обещание ядра. ctx.attach лежал в контракте с первого дня, только тело выбрасывалось: в событие уходило число байт, а сами байты — никуда. Чинить в плагине было нечего. Ядро теперь пишет файл, в событии появилось поле path. Сигнатура attach(name, body, contentType) не изменилась ни на символ — поэтому это @speqkit/plugin-api 0.2.0, а не 1.x: правило «добавление — минор» отработало на первом же настоящем случае.

    Заодно выяснилось, что scope suite был объявлен и никогда не открывался — в контракте три scope, в раннере два. Раннер теперь группирует тесты по файлу, шлёт suite.started / suite.finished и открывает scope между ними.

    Чего гейт не смог — скриншот при падении: хук не видит ни исхода теста, ни способа приложить файл. Записано в открытые вопросы, а не обойдено костылём. Правило «ну один маленький хук» не применялось ни разу.

  5. M4

    Экосистема

    create-speqkit-plugin, test-kit, доки, awesome-speq, заморозка plugin-api на 1.0. Дальше — plugin-vscode, plugin-tui, TS-загрузчик, параллельный прогон. Репортеры оттуда уехали: механизм есть, JUnit есть, остальные форматы — обычные плагины, которые может написать кто угодно.

Что переносится из нынешнего speq

Путь от «работает у меня» до «зелёное в CI» пройден целиком: окружения, репортеры, speq report — и теперь по нему ходим сами, CI на Node 20/22/24. scripts/verify-publish.mjs прогоняет все девять пакетов через настоящие тарболы, временный реестр и одноразовый стор; он же нашёл последнюю дыру — плагин, тащивший за собой ядро, — и теперь плагин берёт ядро через ctx.host. Лицензия MIT, метаданные публикации на месте. Репозиторий выложен — github.com/speqkit/speqkit, — и все девять пакетов опубликованы: ядро как speqkit, контракт и плагины под скоупом @speqkit. Имя закреплено не намерением, а занятыми именами в реестре. Открытых вопросов три. M2 закрыт целиком: standalone-бинарник собран и проверен той же батареей, что и пакеты, ставится через brew и curl … | sh, а плагин может приехать из репозитория — github:, git+ssh:, тарбол по URL, — с коммитом в локе вместо ref'а.
