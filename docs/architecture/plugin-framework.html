A plugin test framework

The kernel is nothing but a plugin loader. HTTP, the CLI, UI tests, reports, a TUI and even control constructs like a loop are all plugins. A new product with no monetisation — a framework for the testing community, by testers. speq-cli goes on living its own cycle; its v1.4 and v1.5 are frozen.

The kernel's contract

The spine

"Everything is a plugin" is never literally true: VS Code hard-wires its contribution points, and pytest's collect → fixture → runtest → report cycle does not move. If the test model is a plugin too, two users of one framework write incompatible tests. So the spine is fixed and does not change.

What the kernel contains — the exhaustive list

Plugin registry + lifecycle   loading, order, dependencies between plugins
Config                        speq.yaml, extends, environment profiles
Test model                    Suite → Test → Step → Assertion, addressable ids
Execution                     order, context, binding results by id,
                              ${...} interpolation, the timeout budget,
                              a re-entrant runSteps() — available to plugins
Resource lifecycle            objects living for run | suite | test
Event bus                     the run's event stream, versioned
Result + artifacts            the model of an outcome and its attachments (binary included)
Validation                    a plugin hands over a schema, the kernel checks a test before the run
Installer                     version resolution, the lock, the plugin cache

The kernel contains none of: a protocol, a CLI command, a report format, a control construct, a UI.

Eight contribution points — and no more opened in v1

Every point that is opened becomes a contract forever: it cannot be closed again. Eight are enough to write http, playwright, postgres, loop, tui and vscode.

  • defineStepTypean id, an input schema, execute(ctx, input) → a result bound by id
  • defineAssertionan id, the kind of target, a schema, evaluate(target, expected)
  • defineResourcea run | suite | test scope, setup/teardown. A browser, a connection pool, a transaction
  • defineReportera subscription to the event bus → output in any format
  • defineValueProvider${...} resolvers: env, a vault, faker, your own sources
  • defineLoaderhow test files are found and parsed. YAML is the default implementation
  • defineCommanda contribution to the CLI surface, through an optional dependency on the cli service
  • defineHookbefore/after at the run, suite, test and step level — for tracing, screenshots on failure, cleanup
Optional dependencies — this works

The postgres plugin wants to add a speq db:seed command, but the CLI may not be loaded — inside VS Code it is not. The plugin declares an optional dependency through ctx.inject(['cli'], …): the command is registered only if the service is up, and the plugin stays fully usable if it is not. This is Cordis's inject pattern, implemented behind the facade by loading in two phases — both cases are covered by tests.

The other direction — ctx.host

The eight points above are what a plugin gives the kernel. ctx.host is what it takes: discover, validate, run, runs, replay, plus the project root, the report directory and the current environment. That side was missing from the contract, and plugin-cli took what it needed the only way available — import { bootstrap, runTests } from 'speqkit'. A plugin runs inside a kernel that is already up and cannot bring its own, which is why Host has no bootstrap and never will: it is the current session, not a way to open a second one. What a plugin and the kernel agree on is still one thing — the major of plugin-api, checked as apiVersion. A plugin needs no kernel version at all.

The event stream

run.started → suite.started → test.started → step.started
  → step.finished → assertion.evaluated → artifact.attached
  → test.finished → suite.finished → run.finished
  ⊥ diagnostic

step.started carries parentId → nested steps are drawn as a tree

The CLI, the TUI, VS Code, a future aggregator and any third-party reporter all stand on this one contract, equally. Get only this right and "many surfaces" follows on its own.

The requirement

A plugin author is not fenced in

Testing the requirement on the hardest case: what is missing is a loop. A loop is not a step type in the ordinary sense — it wraps other steps. If that is expressible as a plugin, everything is.

What the author writes

export default definePlugin({
  name: 'loop',
  setup(ctx) {
    ctx.defineStepType('loop', {
      schema: z.object({
        over:  z.string().optional(),    // ${users}
        times: z.number().optional(),
        as:    z.string().default('item'),
        steps: ctx.schema.steps           // child steps — a type from the spine
      }),
      async execute(ctx, input) {
        const items = input.over ? ctx.resolve(input.over) : range(input.times)
        const out = []
        for (const item of items) {
          out.push(await ctx.runSteps(input.steps, { vars: { [input.as]: item } }))
        }
        return { iterations: out.length, results: out }
      }
    })
  }
})

What the user gets

steps:
  - id: seed
    type: loop              # from speqkit-plugin-loop
    over: ${users}
    as: user
    steps:
      - id: create
        type: http          # from plugin-http
        method: POST
        url: /users
        body: { name: "${user.name}" }

What this asks of the spine — and why the decision has to be taken now rather than later:

  • steps is a first-class recursive type. Child steps are parsed and validated by the kernel, not by the plugin. The plugin receives them already parsed.
  • ctx.runSteps(steps, { vars }) is a re-entrant executor with a child variable scope.
  • Events nest. A parentId on step.started, or neither a TUI nor a report can draw the tree.

Which implies: if, retry, try/catch, repeat-until, foreach-file — all plugins. There is not one control construct in the kernel, and there will never be a need to add one. Not parallel, though: each of those runs its children one at a time, and a second runSteps beside one still in flight is refused. A test runs atomically; suites are what run at once.

Open question

Addressing results inside nested steps. ${seed.results[0].create.body.id} works but is unwieldy; the alternative is flat aliases that the plugin declares itself. To be decided before M1, because it is part of the public DSL.

The main scenario

From "I want to write tests" to a green CI

A payments-service microservice written in Go. Node appears in the repository at no point.

  1. 0

    Install the framework

    brew install speqkit       # or curl … | sh

    Underneath: one executable with the runtime built in: 116 MB on disk, 37 MB in the archive. It can do exactly four things: read the config, install the plugins, bring them up, hand over control. You install speqkit and speq lands on your PATH — the same split as @angular/cli and ng, for the same reason: the name of a project does not have to be the thing typed fifty times a day.

    The runtime inside is a specific version of Node, pinned in scripts/build-binary.mjs and downloaded from nodejs.org against a SHASUMS256.txt check. Not whichever node happened to be on the build machine: a package manager's can be a 66 KB wrapper around a shared library with nothing to inject into — and the runtime version our users get would have become a property of the build machine instead of a decision written down in a diff.

  2. 1

    Initialise it in the service's repository

    cd payments-service
speq init

? Mode ……………… in-repo (tests next to the code)
? Preset ………… @acme/speqkit-preset
? Plugins ……… http, cli  (+ from the preset: postgres, allure)
✔ created .speq/ · speq.yaml · speq.lock · suites/health.yaml

    Underneath: init lives in the bootstrap rather than in a plugin — otherwise there would be nowhere to call it from before the plugins are installed.

  3. 2

    Fetch the plugins

    speq install

  resolving 4 plugins …

    Underneath: the registry is npm, the installer is ours. Plugins land in ~/.speq/plugins/ rather than in the repository. The only thing committed is speq.lock, with exact versions and hashes.

  4. 3

    Write a test

    # .speq/suites/checkout.yaml
name: checkout
steps:
  - id: login
    type: http
    method: POST
    url: /auth
  - id: order
    type: sql               # arrived with plugin-postgres
    query: "select status from orders where id = ${login.body.orderId}"
assert:
  - type: status
    expected: 200
  - type: row_equals
    path: status
    expected: PAID

    Underneath: plugin schemas are handed to yaml-language-server, so completion for type: sql and its fields appears in the editor on its own, with no change to the extension.

  5. 4

    Check it without running anything

    speq validate

  .speq/suites/checkout.yaml:8  unknown step type 'ui'
    ↳ not found among the loaded plugins
    ↳ perhaps: speq add @speqkit/plugin-playwright

    Underneath: the kernel assembles the full grammar of the DSL out of the loaded plugins before the first network call. A typo is caught in milliseconds rather than halfway through a run.

  6. 5

    Run it locally

    speq run --env local
speq run --test suites/checkout.yaml
speq tui                     # if plugin-tui is installed

    Underneath: run-scoped resources are opened (the connection pool), each test gets its test scope (a transaction), and the transaction is rolled back after the test. Data isolation under a parallel run falls out of the same model.

  7. 6

    One more plugin turns out to be needed

    speq add @speqkit/plugin-playwright
speq add github:acme/speqkit-plugin-legacy   # from git
speq plugins                              # what is loaded and what it contributes

    Underneath: add edits speq.yaml, recomputes speq.lock and updates the cache. A company's private scope, a git URL and a local path all work the same way — npm resolution handles all of it.

  8. 7

    Nothing covers it — so write a plugin

    npm create speqkit-plugin loop     # scaffold: src, schema, tests, CI
cd speqkit-plugin-loop && npm run dev

cd ../payments-service
speq link ../speqkit-plugin-loop   # wire it in without publishing
speq run                        # visible in the tests immediately

cd ../speqkit-plugin-loop
npx speq-test-kit               # conformance: timeouts, error, artifacts
npm publish                     # → available to everyone

    Underneath: speq link is the only thing that separates developing a plugin from using one. Publishing is an ordinary npm publish; the author has nothing to agree with you about.

  9. 8

    Put it in CI

    # .github/workflows/tests.yml
- uses: acme/setup-speq@v1
  with: { version: '2.1.0' }
- run: speq install --frozen        # strictly the lock, like npm ci
- run: speq run --env ci --reporter console,junit

    Underneath: --frozen fails if speq.lock has drifted from speq.yaml. The exit code comes from the spine; the reporters are plugins. Bit-for-bit reproducibility of the plugin set, which the current brew install speq cannot offer in principle.

Layout

The file structure

Three different repositories, three different layouts. Locally, a new directory beside the current one, ~/speqkit/; nothing in today's ~/speq/ is touched.

A. The framework monorepo

speqkit/                        # the new GitHub organisation
├── packages/
│   ├── core/           speqkit              the kernel + the `speq` bin
│   ├── plugin-api/     @speqkit/plugin-api        types only — the public contract
│   ├── installer/      @speqkit/installer         resolve, lock, cache
│   ├── plugin-http/    @speqkit/plugin-http       the smoke set, in the box
│   ├── plugin-cli/     @speqkit/plugin-cli        run · validate · list · report
│   ├── plugin-playwright/ @speqkit/plugin-playwright browser, resources, screenshots
│   ├── plugin-tui/     @speqkit/plugin-tui
│   ├── create-plugin/  @speqkit/create-plugin     the scaffold for authors
│   └── test-kit/       @speqkit/plugin-test-kit   conformance tests
├── examples/                     reference projects, e2e
├── docs/                         the spine's spec, the plugin author's guide
├── pnpm-workspace.yaml
└── .changeset/                   package versioning

The monorepo is a deliberate reversal of what today's speq does. Multi-repo is right for a stable product and fatal for a new one: for the first year plugin-api will be changing constantly, and we need atomic edits to the kernel and five plugins in one commit. Third-party plugins live in their own repositories from day one.

An organisation's preset solves the thirty-repository problem

Without one, in six months thirty services carry thirty different plugin versions with no way to update them centrally. A preset is an ordinary npm package in an internal scope: the platform team bumps it and every service updates. It is also the natural place for a company to impose its standards — mandatory reporters, an allowlist of plugins, shared fixtures. extends has to go into the spine straight away: bolting it onto a flat config afterwards hurts.

The contract

Versioning and compatibility

Three things are versioned independently. Confusing them is the most common reason plugin ecosystems become unmaintainable.

WhatThe ruleWho breaks it
@speqkit/plugin-apiStrict semver. A minor adds only; a major is a permitted breakYou, rarely and deliberately
speqkitIts own version. It can climb through majors without touching the plugins, as long as plugin-api is the sameYou, freely
Each pluginIts own version. Declares peerDependencies: @speqkit/plugin-apiIts author
The DSLversion: 1 in speq.yaml. Migrations with a clear messageYou, at majors
The event schemaVersioned separately — external consumers stand on itYou, additively

The compatibility rules

  • A plugin is compatible with the kernel if and only if the major of plugin-api matches.
  • The kernel checks that at load time and refuses to load an incompatible plugin with a clear message — rather than falling over halfway through a run.
  • The kernel supports the N−1 major of plugin-api for at least 12 months. Without a deprecation window, serious plugin authors will not invest.
  • speq.lock holds exact versions and hashes; --frozen in CI gives bit-for-bit reproducibility.
  • An organisation's preset pins versions for every service at once.
The stability promise has to be said out loud

0.x — we break anything, without warning. 1.0 — plugin-api is frozen for the major. Until that line is in the README there will be no ecosystem: nobody writes a plugin against a contract that might vanish.

Needs a decision

Open questions

Three are left, and the first of them is closed. Two old ones and one the gate found. The two that were dropped stay dropped: there will be no monetisation, and v1.4 / v1.5 are frozen.

  1. The name — decided. The project is called speqkit and the terminal command is speq. The @speqkit scope on npm and the github.com/speqkit organisation are ours. It did not come about out of abundance: of ninety candidates checked, not one dictionary English word is free on npm, and speq is held by an abandoned 0.0.0 placeholder and by a live, unrelated @speq-ai/speq. Splitting the package name from the binary name is ordinary practice (@angular/cli gives you ng), and it buys a clean namespace on all four axes with four characters under the fingers. The kernel is published as unscoped speqkit so that the install line reads npm i -g speqkit rather than like installing somebody's internals; the @speqkit scope stays for the plugins and the contract. A command name is nobody's namespace at all, and there is no one to take it from.
  2. Addressing results inside nested steps. Today ${seed.results[0][0].body.id} works — precise, but unwieldy. The alternative is for a plugin to declare a flat alias itself. Part of the public DSL, so before 1.0.
  3. Screenshot on failure: what the hook can see. Found by the gate, not invented. HookPayload in test:after carries neither the test's outcome nor attach — a plugin physically cannot learn that the test failed and attach the image proving it. Two ways out: either the hook gets the outcome and the ability to attach an artifact, or catching a failure becomes a step — try/catch as a step type, by exactly the same move as loop. The second is more honest towards "control flow is a plugin", but it requires a step to be able to catch its neighbour's failure. Part of the public contract, so before 1.0.
  4. Cordis — behind the facade or not. The registry is ~170 lines of our own behind the PluginContext interface; services and optional injection already work. Swapping the internals for Cordis is a one-file change and plugin-api would not see it. M2 came and went and the need for HMR never arose: the decision is deferred again, now until the 1.0 freeze. The facade was built precisely so that deferring costs nothing.
The plan

Milestones

  1. M0

    A prototype of the spine · done

    A kernel with a type registry, two dummy plugins, one YAML test. The goal was to see whether the spine holds, before deciding on the name and freezing the roadmap.

  2. M1

    The spine stands · done

    core + plugin-api + plugin-yaml + plugin-http + plugin-cli + plugin-loop. A YAML test passes end to end against a real API, and there is not one mention of HTTP in the kernel. 12 architecture tests green, types clean.

  3. M2

    The installer · done

    The main technical risk turned out to be exactly where it was expected, and is largely taken. speq install talks to the npm registry over HTTP itself: resolves a range, downloads the tarball, checks sha512, extracts, lays out the store and writes speq.lock. Neither npm nor pnpm nor yarn is invoked — requiring the very package manager we are replacing would cancel the whole idea.

    The store's layout is pnpm's, and for pnpm's reason. A dependency is a symlink inside the directory of the package that depends on it, so ordinary Node resolution, which walks real paths, finds it — and two plugins can want different versions of one library. The links are relative, so the store stays portable. Verified for real: chalk@^4.1.2 with six transitive dependencies installs and imports out of the store.

    Presets shaped the installer. extends names an npm package, which means the config cannot be read until that package is on disk. So the installer takes two callbacks rather than two lists, and makes the passes in the right order itself.

    Working: --frozen (installs strictly from the lock and fails on any drift from speq.yaml), add/remove (edit speq.yaml through the YAML document, so comments survive), link (beats both the store and node_modules), doctor (says which plugins came from node_modules and therefore will not reproduce in CI).

    The road to a green CI is closed — and it found the third hole of the same kind the gate found twice. environments/ had existed since M0 and nobody read it: there was no --env flag at all. An environment is now a layer of settings on top of speq.yaml, and only settings: it cannot add a plugin, because the plugin set is fixed by speq.lock and speq install --frozen runs in CI before anyone has said which environment the run will use. An environment able to drag in a plugin would produce a lock that is correct for local and one package short for ci. Config files expand ${env:NAME} and ${env:NAME:-fallback}, and an unset variable is an error rather than an empty string: otherwise the suite quietly aims at localhost and goes green against nothing. ${login.body.id} is left alone — that syntax belongs to the run.

    defineReporter had been in the contract since the first commit, and not one plugin called it. Console output went straight to events.subscribe — around the mechanism rather than through it. That is exactly what the gate found in attach and in the suite scope, and it is fixed the same way: the console became an ordinary reporter and the default value of --reporter, so that the mechanism carries the most travelled path. ReporterDef gained an optional init(ctx) with runId, outputDir and runDir — a reporter writing a file had no way to learn where to write it. An optional method, hence plugin-api 0.3.0, with PLUGIN_API_VERSION still 1.

    Every run writes its events to events.jsonl, and speq report replays them into the same bus. That is not a convenience, it is how the architecture's central claim gets checked. If the event stream really is the contract that reporters, the TUI and a VS Code panel stand on, then a report built from the recording has to match the report of a live run. @speqkit/plugin-junit builds its XML out of RunEvent alone, with no access to the runner's result, and the test demands a byte-for-byte match. On the day the event stream stops describing a run in full, it will be found there rather than in somebody else's plugin six months later.

    Building and verifying what gets published. Every test in the repository reaches src through a bundler alias — and precisely that hid the fact that exports pointed at TypeScript while Node refuses to strip types inside node_modules: a package published that way would not have loaded at all. The packages are built with project references (tsc -b) into dist, and scripts/verify-publish.mjs trusts none of it: it packs the real tarballs, brings up a throwaway registry over HTTP, installs into a throwaway store, and runs the CLI out of dist with plain node in a directory that has no node_modules anywhere in it. "The installer is tested against other people's packages but not our own" is closed.

    The harness found a fourth hole of the same kind, and this time it was not the gate. plugin-cli declared speqkit as an ordinary dependency — because the contract gave a plugin no way whatsoever to reach the kernel it was running in. The cost was double and completely silent: the installer faithfully put a second copy of the kernel into the store and pinned it in speq.lock, while the plugin itself called bootstrap() inside a process that had already booted. Two registries, every plugin loaded twice per invocation, and the kernel answering is not the one the user installed but the one the lock pins. All green, and all wrong. The fix is the same as in the three earlier cases: the missing direction was added to the contract rather than worked around. ctx.host appeared, plugin-cli does not import the kernel in a single line, and its package.json names only plugin-api as a peer. The invariant is pinned from both sides: a test fails if any plugin's manifest mentions the kernel, and the harness fails if the kernel ever ends up in the store. Additions only, hence plugin-api 0.4.0, with PLUGIN_API_VERSION still 1.

    Step zero is closed. scripts/build-binary.mjs builds a single executable: the kernel, the installer and yaml are bundled into one CommonJS file, Node SEA places it as a blob inside the official runtime, postject injects it, macOS re-signs it. Plugins deliberately do not go inside — they are still loaded at runtime by absolute path out of ~/.speq, and an import() from inside the blob reaches the real filesystem. A binary with the plugins baked in would be a different product — precisely the one all of this was written to avoid.

    The proof is not a separate thing but the same one: verify-publish.mjs gained a --binary flag and points the same battery at the executable with PATH=''. Install from a throwaway registry, six packages into the store, four plugins loaded out of it, a suite run, --frozen with the registry unreachable — all of it where node cannot be reached in principle. Two delivery routes, one definition of the word "works". Startup is 30 ms: the blob carries a V8 cache, which is also why it is built by the very runtime it is injected into.

    Delivery: packaging/install.sh (curl … | sh, sha256 checked, and on a mismatch nothing is installed), packaging/homebrew/speqkit.rb, and scripts/render-formula.mjs, which refuses to render a formula if the release is missing any one of the four platforms: a tap that is correct on three and silently absent on the fourth is worse than no tap. release.yml builds darwin/linux × arm64/x64 on native runners — cross-compilation is impossible because of that same V8 cache, and because only macOS can re-sign a Mach-O.

    The macOS signature is ad-hoc, and that is a final state rather than an open item. Notarisation costs an Apple Developer account and a certificate in CI, and buys nothing on either of the routes people actually install by: brew clears the quarantine attribute itself, and a file fetched with curl never gets one. Gatekeeper stops only what a browser downloaded — and the answer to that is the install script, not a certificate. Decided: there will be no notarisation.

    A plugin can now come from somewhere other than a registry. github:acme/plugin#v2, gitlab:, bitbucket:, git+ssh://…#main, git+file://, and a tarball by URL. A ref is resolved to a commit at install time and only the commit goes into the lock: #main means something else a month later, and --frozen in CI has to install what was reviewed. The commit goes into the store key as semver build metadata — 1.4.0+8f2c1ade9b7c — because two commits can carry the same version, while a dependency asking for ^1.4.0 has to stay satisfied.

    The git specifiers call git — a deliberate exception to the rule everything else obeys. We go around the registry ourselves because npm is exactly the tool being replaced; requiring it would cancel the idea. Git is not being replaced by anything, it is already installed by whoever owns the repository, and calling it buys three things no hand-written HTTP would give: private repositories work through credentials and an ssh agent that are already configured, self-hosted instances need no per-vendor API dialect, and the commit is verified by git rather than by a vendor's JSON. It is needed only by the git specifiers — nowhere else, the standalone binary included.

    A build is never run. Refusing to execute install scripts is what makes installing from a repository defensible in the first place, so a repository with no committed entry point is rejected at install time with an explanation, rather than installed cleanly and failing minutes later inside a plugin loader that cannot say why. A tarball by URL is hashed on arrival and the hash goes into the lock: there is no registry here to vouch for it. And the registry token no longer travels to a host that is not the registry — it used to go to whichever host's URL happened to be in the packument.

    Not done: of the delivery channels there is no Docker image and no setup-speq — both are wrappers around an artifact that is already built, and both live in separate repositories. .npmrc is not read; a private registry works through SPEQ_REGISTRY and NPM_TOKEN.

  4. M3

    The gate · passed

    plugin-loop went first: the loop and retry were written against the published API, the kernel did not change once, and nested steps execute in a child scope. plugin-playwright finished off the other half — scoped resources and binary artifacts, the parts of the spine the loop never touched. A live Chromium, two tests, and a 1280×720 PNG that reaches the disk byte for byte.

    Resources passed without a single kernel edit. Three scopes, a resource depending on a resource (page → context → browser), config reaching setup, teardown in reverse order even when the test fails, an assertion fetching page itself with no step in front of it. One browser for the whole run: the second test opens a page in 222 ms against the first test's 2463 ms.

    Artifacts did not pass — but it turned out to be an unkept promise of the kernel rather than a fault in the spine. ctx.attach had been in the contract from day one, only the body was thrown away: the event carried a byte count and the bytes themselves went nowhere. There was nothing to fix in the plugin. The kernel now writes the file and the event gained a path field. The signature attach(name, body, contentType) did not change by one character — which is why this is @speqkit/plugin-api 0.2.0 rather than 1.x: the "an addition is a minor" rule worked on the first real case.

    It also emerged that the suite scope was declared and never opened — three scopes in the contract, two in the runner. The runner now groups tests by file, emits suite.started / suite.finished, and opens the scope between them.

    What the gate could not do — a screenshot on failure: a hook sees neither the test's outcome nor any way to attach a file. Written down in the open questions rather than worked around with a hack. The "well, just one small hook" rule was not applied once.

  5. M4

    The ecosystem · started

    @speqkit/test-kit and create-speqkit-plugin are done. The kit runs a plugin inside the real kernel — the same Registry, the same Executor, the same runner speq run uses. There are deliberately no fakes in it: a mock ExecContext would be a second implementation of plugin-api, written by us and drifting from the first, and all it would prove is that the plugin agrees with our mock. The kit adds exactly two things the kernel does not otherwise give a plugin author: a project root on disk — because ctx.host on a hand-assembled registry throws — and a scope stack held open between calls, so that ${id.field} works the way it does in a test file. Which is why speqkit is a peer of the kit rather than a dependency: an author checks their plugin against the kernel they intend to support.

    npm create speqkit-plugin kafka produces a package with the decisions that are easiest to get wrong already made: the contract is a peer, the kernel is not among the dependencies, the step type and the assertion carry schemas, and the speqkit-plugin keyword is in place. The tests in it are written against the kit and they pass. The versions the generator writes into package.json are hard-coded — at the moment npm create runs there is no workspace to read — and pinned by a test to the real package versions so they cannot go stale.

    The kit found the fourth hole of the same kind the gate found twice. AssertContext.results was described in the contract as "the results of every step" and was always empty, and ${a.value} in an assert: block answered that a was not defined. The executor opened a frame on every runSteps call and popped it on the way out — including the outermost one, the frame holding the bindings of the test's own steps. Assertions are read after it. Inside a single runSteps the frame is still there, so steps always saw each other and the hole hid in exactly the one place nobody looked. The outer call now runs in the base frame; nested ones still run in child frames. Plus the two tests that were missing.

    Along the way plugin-loop and plugin-yaml got tests of their own — six published plugins had not one between them — written the way an outside author would write them: through the kit, without a single reference to the kernel's internals. The structural ban "a plugin does not depend on the kernel" had to be narrowed to what a user actually installs: dependencies, peerDependencies, optionalDependencies and imports in the sources. devDependencies came out of it — a plugin's tests bring up the real kernel, and that is the whole point of the kit.

    Three author scenarios were checked the way the gate checked the spine — with plugins, not with reasoning. A client we never shipped (mongodb): passes in full, a run-wide resource, config, exec.signal, and the plugin's own dependency really is installed and linked in the store — yaml@2.9.0 sits there under plugin-yaml, a driver will arrive the same way, and a heavy one can be declared an optional peer, as playwright is. Schemas in .speq/: ctx.host.root is available inside setup() already, and the file is read at assertion time. Variables a test writes: done through defineValueProvider plus the plugin's own state, and they outlive the test, which step results cannot.

    Of the four holes found, the first and most expensive is closed. A plugin had nowhere to report an error a schema does not catch: that a schema file is missing, that over and times are both set. It came out halfway through a run, from a step type that cannot name the file. StepTypeDef and AssertionTypeDef now have validate — contract 0.5.0, an addition, PLUGIN_API_VERSION still 1. Walking the tree from the plugin would have been the natural design here, and it was not taken: traversal and addressing stay with the kernel, a plugin returns messages and at most a path inside its own step, so it cannot lie about location. Synchronous on purpose — validation runs before every run, so reading a file is fine and going to the network is not. A validator that throws becomes a diagnostic about the plugin rather than a collapse of the whole validation. plugin-loop already uses it.

    The second hole is closed, and with it the only blocker to the freeze. ValueProviderDef.resolve was always declared as unknown | Promise<unknown>, and lookupPath did not await it: an asynchronous provider put a Promise straight into the request body, silently. We chose to await it honestly rather than narrow the type to synchronous: a secret from a vault and a row from a database are precisely the case a provider exists for. To keep that asynchrony out of the contract, resolution is split in two: prime asks the providers and awaits all of them at once, while the walk that substitutes values into ${...} stays synchronous and reads answers that are already there. So ExecContext.resolve, resolveDeep and AssertContext.resolve kept their signatures — no plugin became asynchronous because of a provider it does not use — and the contract's types did not change at all: the kernel finally does what was written there from the beginning.

    Three decisions had to be taken on the way. A provider is asked once per pass rather than once per mention: it is a lookup, not a generator — but a pass is exactly one step wide, so a value that changed between two steps is read afresh by the second. All of a step's keys go to the providers at once rather than one after another, and the error that surfaces is the first in template order rather than the first in time — otherwise the diagnostic would depend on who answered fastest. The wait happens under the step's timeout: a provider that went to the network and never came back is a step taking too long, not a hung run.

    Two holes remain, and both are additions after 1.0. A step cannot put a value into its own scope: ${vars:token} works, ${token} does not, and there is no exec.set(). exec.vars hands back only the innermost frame, although ${...} resolves the whole stack. Neither breaks the contract, so both land after the freeze.

    Left to do: the docs, awesome-speq, and freezing plugin-api at 1.0 — the last of which is held up by three open questions, two of which change the public contract. After that: plugin-vscode, plugin-tui, the TypeScript loader, parallel runs. Reporters left that list: the mechanism exists, JUnit exists, and the remaining formats are ordinary plugins anyone can write.

What carries over from today's speq

The only thing thrown away is the Rust implementation — about 5,600 lines, and the cheapest part. Everything expensive carries over: the design of the YAML DSL, the semantics of seven assertion types, the report contract, the exit codes, the Allure output, the in-repo/test-repo modes, the documentation. The spec for plugin-http is 80% today's docs/cli/README.md.
