Writing declarative tests

A test is data. It declares what must be true and never says how to check it, which is what lets the same file be run by a terminal, an editor, or something nobody has written yet — and what lets speq validate find a mistake in milliseconds without a service being up.

The shape

Eight fields, and the list is closed

One file, one test — or several, separated by ---. Everything except steps is optional, so the smallest useful file is two lines. 

# .speq/suites/menu/create-item.yaml
id: menu.items.create
title: POST /categories/{id}/items creates an item
tags: [smoke, menu]

variables:
  slug: "${gen:uuid}"

setup:
  - id: tenant
    type: use
    ref: register-tenant

steps:
  - id: created
    type: http
    method: POST
    url: "/categories/${tenant.categoryId}/items"
    body: { name: "speq-${slug}", price_cents: 1200 }
    assert:
      - type: status
        expected: 201

assert:
  - type: equals
    path: created.body.name
    expected: "speq-${slug}"

cleanup:
  - type: http
    method: DELETE
    url: "/items/${created.body.id}"
  • idthe test's identity — stable, and what every event carries
  • titlethe sentence a person reads, when the identity is not one
  • tagswhat --tags filters on
  • variablesthe test's givens, resolved once before anything runs
  • setupbuilding the world this test needs
  • stepswhat it does
  • assertchecks over the whole test, after the last step
  • cleanupwhat runs afterwards, whatever happened
Why closed

Everything outside that list is an annotation and travels in meta — see below. The list has to be closed for the annotations to be open: if owner: could be a spine field, every team's field would become a contract of ours, and there are as many of those as there are teams.

Steps

A step does something and publishes what it found

Every step has a type, which names the plugin that owns it, and optionally an id. The id is how later steps read what it produced: ${created.body.name}. A step without an id runs and publishes nothing, which is the right choice for the ones nobody refers to. 

steps:
  - id: menu
    type: http                    # @speqkit/plugin-http
    method: GET
    url: /restaurants/${slug}/menu

  - id: each
    type: loop                    # @speqkit/plugin-loop
    over: "${menu.body.categories}"
    as: category
    steps:
      - type: http
        method: GET
        url: "/categories/${category.id}/items"
        assert:
          - type: status
            expected: 200

An unknown key is a mistake, not a comment. A step's schema is closed, so bodyRaw: where the plugin expects body: is a diagnostic from speq validate before any request goes out. This is not pedantry: the suite this framework was designed against had six such keys silently ignored, three upload paths with no coverage at all, and a green tick on every run.

Assertions belong to the step that produced the result

A check on a response is written under the step that made the request, not at the bottom of the test in a block that has to name it again. Both places exist and mean different things: assert: on a step is about that step, assert: on the test is about the whole thing — usually comparing two steps, or a step against a given.

Control flow is a plugin

loop, repeat and retry come from @speqkit/plugin-loop and the kernel contains none of them. The plugin calls back into the executor through ctx.runSteps with its own child variable scope, which is also why ${category} inside the loop does not exist outside it.

Values

One substitution syntax, four kinds of answer

Everything is ${…}. A bare name reads a binding — a variable, or an earlier step's result. A prefix asks a provider, and a provider is just another plugin contribution.

  • ${step.field}what an earlier step published, by its id
  • ${gen:uuid}a value made for this test — uuid, string, int, email, date, or one you declared
  • ${env:NAME}the process environment. ${env:NAME:-fallback} when it is optional; unset and without a fallback is an error, not an empty string
  • ${vars:name}a project value from data.vars, tuned per environment file
  • ${meta:owner}an annotation off the running test

Variables are where a generated value gets its name

variables:
  slug: "${gen:uuid}"
  foreignSlug: "${gen:uuid}"          # a different uuid
  email: "speq-${slug}@example.com"   # written in terms of the one above
Resolved one at a time, in order

That is not an implementation detail. A block resolved in a single pass would hand slug and foreignSlug the same uuid, and the test that exists to prove two tenants stay apart would be checking one tenant against itself — silently, and forever green.

Generated values are derived from a seed rather than drawn from the system random source, and the seed is the run id — the same string that already names the report directory. Replaying a run's data means copying a string off the screen, and a single failing test re-run on its own sees exactly what it saw inside the suite.

The vocabulary

Twenty-one words over one selector

Every assertion asks the same two questions: what are we looking at, and what must be true of it. The first is one selector shared by all of them. Learning the plugin is learning that selector and a list of words.

SelectorMeans
path:a dotted path into the step's whole result, with [n] indexing
value:an explicit value, usually a template — for checks that are not about the last step
neitherthe whole result

Why body. and not just the field. path reads into the step's whole result, not into a body it assumes is there. An HTTP step returns { status, body, text, headers, durationMs }, so a check on the payload is path: body.items[0].sku. That extra word is exactly what the plugin buys: the same at_least reads a SQL row, a file's contents and a browser's page state, because nothing in this vocabulary believes it is looking at a response.

Equality — structural

  • equals
  • not_equals

Order

  • greater_than
  • at_least
  • less_than
  • at_most

Membership, from both sides

  • contains — substring, array element, object key
  • not_contains
  • one_of — the subject is one of a list
  • not_one_of

Text

  • matches — a regex, refused before the run if it does not compile
  • starts_with
  • ends_with

Presence

  • exists
  • missing
  • empty
  • not_empty

Size and shape

  • length — expected, or at_least / at_most
  • is_type
  • schema — a JSON Schema file, through ajv

A failure names the subject, the requirement and what was there

expected body.price_cents to be at least 900, got 450
body.categories does not match menu/menu.schema.json: /0/status must be equal to one of the allowed values
body.discount is not there

A path that leads nowhere is reported as that, not as a comparison against nothing — is not there, rather than expected at least 900, got undefined, which reads like a wrong number when the field is simply missing. The four presence checks are the exception, because a missing path is the question they are asking.

schema, by a real implementation

Validated through ajv, against draft-07 as written. A hand-rolled subset is the tempting version and the dangerous one: schemas generated from OpenAPI arrive with oneOf, $ref and patternProperties, and a validator that quietly ignores keywords it does not understand reports a pass it never performed. A gate that lies is worse than no gate.

Schemas are compiled during speq validate, so a typo in one is found in milliseconds: 

suites/menu/lists-items.yaml
  assert[2].ref  no such schema: /repo/schemas/menu/itmes.schema.json
Deliberately absent

No and / or / not. A block already reads as "all of these hold", every assertion in it runs, and each reports for itself — which is precisely what a combinator would take away. And no custom comparators: a check this list does not have is twenty lines in a plugin of your own, through the public defineAssertion, not a pull request against ours.

Composition

use — calling something declared somewhere else

In the real 60-test suite this framework was designed against, use outnumbers the HTTP step it composes, 179 to 115. Composition is the most common thing a suite does, which is why it is one plugin, one keyword and three forms rather than three filing-cabinet dividers a tester has to learn. 

steps:
  - id: setup
    type: use
    ref: register-tenant          # shared/register-tenant.yaml

  - id: category
    type: use
    action: menu.createCategory   # modules/menu.yaml, action createCategory
    properties:
      accessToken: "${setup.token}"
      name: "starters"

  - id: item
    type: use
    fixture: menu-item            # fixtures/menu-item.yaml
    overrides:
      name: "speq-item"

  - type: http
    method: POST
    url: "/categories/${category.id}/items"
    body: "${item}"

A use step is a step: it binds by id like every other one, and ${id.…} reads what it published. That is the one meaningful difference from how v1 worked, and it is the point of the migration — a shared block used to publish its own ids straight into the calling test, so ${tenant.token} appeared with nothing to say where tenant came from. Now the block runs in its own scope and hands its result back through the step that called it. A leak became a written-down name.

Setup and cleanup

Building a world, and putting it back

setup and cleanup are the kernel's, not a plugin's — a plugin cannot express finally without leaking its child scope back into the caller, which is the invariant the scope exists for.

Cleanup runs whatever happened

Including after a setup that never finished — which is exactly the moment the rows a half-built test created would otherwise be left behind forever.

A test that could not clean up is error

Not passed. It answered its own question and then left something behind, and the next run inherits it. A verdict already reached is not overwritten, though: a test that failed reports the failure — that is the news.

Annotations

Everything else the test carries

link, owner, epic, severity, a ticket number — there will be as many of these as there are teams. So the spine is closed and everything outside it is meta, which the kernel carries and never reads. 

id: menu.items.create
title: POST /categories/{id}/items creates an item
owner: mira
epic: menu
jira: SHOP-4417

Nothing has to be declared. On a step it goes under a reserved meta: instead, because every other unknown key there already belongs to the plugin that owns the step's type — the kernel lifts it out before the schema is checked.

It reaches test.started and both step events, so a reporter gets it for free, and it is readable while the test runs — an x-owner header on every request needs no plugin: 

steps:
  - type: http
    method: GET
    url: /orders
    headers:
      x-owner: "${meta:owner}"
The line meta does not cross

Meta describes a test; it never controls one. The moment behaviour follows from an annotation — retries: 3, skip: true, parallel: false — a suite has control flow that speq validate cannot see, a report cannot explain and a user cannot find. Behaviour is a step type or a config key: something declared, and something checked. The kernel never branches on meta, and that is an invariant rather than a current implementation.

Parking a test

pending takes a reason, not a flag

id: menu.items.bulk-upload
pending: "blocked on SHOP-4417 — the endpoint 500s on files over 2 MB"

A test parked without a reason is a test being deleted slowly, and the reason is the only thing that makes the entry worth keeping over git rm. A pending test is still validated, because it is precisely the test nobody runs and therefore the one that rots unnoticed.

Running them

The commands

speq validate                              # typos, schemas, unknown keys. No network.
speq run                                   # everything
speq run --tags smoke                      # by tag
speq run --test suites/menu/create.yaml    # one file
speq run --suite suites/menu               # one directory
speq run --env ci --reporter console,junit
speq report --list                         # runs already recorded
speq report                                # re-render one, without re-running it

--env ci layers an environments/ci.yaml of settings — and only settings. An environment cannot add a plugin, because the plugin set is what speq.lock pins and speq install --frozen runs in CI before anyone has said which environment the run will use.

Coming from speq v1

speq migrate

Rewrites {{x}} to ${x}, type: api to type: http, $steps.a.response.body to ${a.body}, a folded bodyFromFixture into the use step it always was, and manifest.yaml plus environments/* into a speq.yaml with layers. Comments survive, because a suite of any size is documentation as much as it is tests.

What has no successor is named, never dropped. A suite-level beforeEach, a v1 retry policy — these are reported by file with what to write instead. A codemod that silently discards what it does not understand leaves a suite that still goes green with the guard simply gone.

Reference for each plugin lives in its own README: yaml, http, assert, data, use, loop.
