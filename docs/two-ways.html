Two ways to work

speqkit is an instrument of execution. Whether the acceptance criteria exist before the code or arrive after it is your team's decision, and the framework serves both without having an opinion about either. What actually differs between them is one thing: which of red and green is the starting state.

Orientation

Which one you are in

Both are ordinary, and most repositories hold both at once. A feature that arrives with acceptance criteria attached gets its tests before anybody writes an endpoint; the billing code that has been in production for six years gets covered after the fact, because it already works and the point of covering it is to keep it working. The question is never about the project. It is local to the change in hand.

  • Tests firstthe criteria are known before the implementation, and the suite is what "done" means
  • Code firstthe behaviour exists, and the suite is what stops it from quietly changing
The join is a tag, and only a tag

speq does not read your specification — not a Jira ticket, not a Spec-Kit or OpenSpec repository, not a page in a wiki. It has no idea what a requirement is. The only link between one and a test is a tag somebody wrote, and there will not be a second one. What to cover is your decision; what speq promises is that the answer comes back fast and says enough to act on.

Tests first

The gate is built before the thing it guards

Sometimes called ATDD, and the name matters less than the shape: the acceptance criteria are turned into runnable tests before the code exists, so that "is it done" stops being a conversation and becomes an exit code. It is also the arrangement that makes generated code safe to accept, because the check was written by somebody who was not trying to pass it.

  1. 1

    The requirement arrives, in whatever form your team uses

    Not our business, and deliberately so. What comes out of this step is a key you can write down — a ticket id, a feature name, anything stable — and from here on that key is the only thing speq knows about it.

  2. 2

    Branch, then write the tests into it, tagged with the key

    The branch is named for the key and so are the tags. That one convention is what makes every command below able to find exactly this piece of work and nothing else. 

    # .speq/suites/payments/refund-partial.yaml
id: payments.refund.partial
title: a partial refund leaves the rest of the order captured
tags: [PAY-114]

steps:
  - id: refund
    type: http
    method: POST
    url: "/orders/${order.id}/refunds"
    body: { amount_cents: 400 }
    assert:
      - type: status
        expected: 201

assert:
  - type: equals
    path: refund.body.remaining_cents
    expected: 600

    The first command is not run. speq validate --tags PAY-114 checks the whole file against the grammar the loaded plugins define — every step type, every assertion, every closed schema — in milliseconds, with nothing deployed and no service up. A criterion with a typo in it is not a criterion, and this is the cheapest moment in the whole process to find that out.

  3. 3

    Run them and watch them fail

    speq run --tags PAY-114
# 0 passed, 3 failed — the endpoint answers 404, which is correct: it does not exist

    This is not a broken build. It is the gate reporting that the work is not done, which is the only honest thing it can say. From here the suite has exactly one job: to turn green when — and not before — the feature is real.

    Why the branch, and why not pending

    A suite that is red on purpose belongs where the code is being written and nowhere else. Merged to main it makes the default branch permanently red, and a build that is always red is a build nobody reads. The branch already is the mechanism: the tests go green as the code lands, and the two arrive together.

    The other temptation is to park the new tests with pending: until the feature exists. Do not. pending does not run — it reports skipped and moves on — and a criterion that does not run is not a gate. It is for a gap you have decided to live with, like a 429 path you cannot reach from a stack configured to survive the rest of the run, and the reason it takes a sentence instead of a flag is that somebody has to read that sentence later.

  4. 4

    Implement until it goes green

    The loop narrows as it goes. Start with the ticket, drop to the one test that is still red, and ask for the exchange when the message is not enough. 

    speq run --tags PAY-114              # everything this ticket is answerable for
speq run --name payments.refund.partial   # the one that is still red
speq run --name payments.refund.partial --verbose  # with the request and the response
    There is a plugin for the convention

    Everything above is --tags and a branch name, and it stays that way. @speqkit/plugin-gate is the same thing with the key read out of the branch and the answer written down: speq gate plan says what would run and why, speq gate runs it, and gate.json routes every red test to the code, the test or the environment. On demand, like every layer-two plugin — nothing on this page needs it.

    Re-running one test is not a different test. Generated values come from a seed and the seed is the run id, so a single test re-run alone sees exactly the data it saw inside the whole suite — which is what makes the narrow loop trustworthy rather than a second experiment.

  5. 5

    When the test is the thing that is wrong

    It happens, and it is not misconduct. A criterion written before the code sometimes asserts on a field that ended up with a better name, or encodes an assumption that turned out to be false. Change it — in the same pull request, next to the code that made you change your mind.

    Tests here are data, so the amendment is legible. A YAML diff says exactly which assertion moved and to what, which is a thing a reviewer can agree or disagree with. What is worth establishing in your team is only that such a diff gets read as an amendment to the acceptance criteria rather than skimmed as test churn.

  6. 6

    The pull request runs everything

    speq install --frozen     # the plugin set that was reviewed, by commit
speq run --workers 4 --reporter junit,console

    The ticket's own tags got you here; the merge is answerable for the whole suite. --frozen installs what speq.lock pins rather than wherever a tag has moved since, so the gate that passes is the gate that was reviewed.

Code first

The suite follows the feature

The ordinary way, and the one most suites in the world are written in. The behaviour exists; you are writing down what it does so that it cannot change without somebody saying so. Nothing about the framework is different here — the same files, the same vocabulary, the same commands.

  1. 1

    Organise by the service, not by the tickets

    Directories follow the shape of the thing under test, because that is what somebody will be looking for in a year. Tags are labels — smoke, orders, slow — rather than keys, and they exist to answer "what do I run right now". 

    .speq/suites/orders/list.yaml
.speq/suites/orders/refunds.yaml
.speq/suites/orders/suite.yaml    # what every test below it shares
  2. 2

    The loop is the file in hand

    speq validate --test .speq/suites/orders/refunds.yaml
speq run --test .speq/suites/orders/refunds.yaml
speq run --name orders.refund.partial --verbose
  3. 3

    Make it fail once, on purpose

    The one cost of this direction

    A test written against working code is green from its first run, and a test that has never been red has not been shown to be able to go red. An assertion on a field that no longer exists, a selector that matches nothing, a check on a response that is never reached — each of them passes quietly forever.

    So break it deliberately once: change the expected value, watch it report the difference, change it back. Ten seconds, and it is the only evidence you will ever get that the test is connected to the thing it is testing. In the other direction this is free — a suite written before the code is born red, and every one of its tests has been observed failing before it was ever trusted.

  4. 4

    The gate is the whole suite

    There is no ticket to scope to, so CI runs everything and the exit code is the verdict. --shard i/n across machines, --workers within one, and both compose.

The overlap

What does not differ

Nearly everything. This is worth stating plainly, because a page with two halves invites the suspicion that there are two tools in here.

  • The filethe same nine fields, the same YAML, the same loaders
  • The vocabularythe same step types and the same 21 assertions
  • The checkspeq validate before the network, in both directions
  • The datagenerated from the run id, so a re-run is a replay and not a new experiment
  • The reportone event log, and every reporter built out of it
  • The verdictthe exit code, which is the only thing CI reads

Which of red and green is the starting state is the whole of the difference. Everything else is your team's arrangement of branches, reviews and gates — and speq has no opinion about those, on purpose.

Machines

When a model writes the first draft

Both directions survive a generated suite, and the tests-first one is where it pays: the acceptance criteria are written by something that is not the thing being graded, and they are checkable before a single request goes out. That last property is not rhetoric — it is why the tests are data. A generated suite can be validated without being executed; a generated test file in a programming language cannot, because finding out whether it is even loadable means running arbitrary code.

  • speq capabilities --jsonthe grammar as it actually is in this project — every step type, assertion and value provider with its schema, so a prompt is not a copy that goes stale the moment a plugin is installed
  • speq docs --jsonthe same vocabulary with a sentence and a working example beside each word. A schema says what shape is accepted; this says what it is for, which is the half a generator was previously guessing at
  • speq modules --jsonwhat this project has already built — the shared blocks and module actions, with the properties each takes. Without it a generator reaches for the transport and rebuilds a login that exists
  • speq validate --jsonevery problem with a code beside the message: an unknown step type is a different thing from a malformed template, and telling them apart decides what to fix
  • speq run --jsonthe counts, and per test the failures — with what was expected, what was actual, and what the step was doing
  • speq run --verbosethe same, for a person: the request and the response of a step that did not pass, without running it again behind a proxy
Failed and errored are not the same news

A step that failed means the system answered and the answer was wrong — go and look at the code. A step that errored means the question was never properly asked: a template that would not resolve, a plugin that threw, a service that was not listening. The distinction has been in the kernel since the first commit and it is the cheapest routing signal there is, whether the thing reading it is a person or a repair loop.

The line

What we do not decide

A test framework that had opinions about branches would be wrong about them for most of the teams using it. These are yours:

Yours

  • The specification, in any format
  • What gets covered, and to what depth
  • Branch naming, protection and merge rules
  • Whether a criterion may change, and who agrees to it
  • Which tests block a merge

Ours

  • That a mistake in a test is found before the network
  • That a failure says what was expected, what came back, and what the step was doing
  • That one test can be re-run alone and see what it saw
  • That the verdict is an exit code and a document
  • That anything missing can be added as a plugin

And one field we decided not to add. The obvious request from tests-first teams is a way to declare a test red on purpose — expected: fail, the way pytest has xfail. There is no such field, because the branch already does that job and does it better: the test is red where the work is happening and green by the time it merges, so the default branch never has to be told to expect bad news. A field the kernel branched on would be control flow that speq validate cannot see.

The language itself is on Writing declarative tests; what the kernel owns and what it does not is on the overview.
