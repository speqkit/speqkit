Overview

The map of the pipeline

Seven stages. You walk the first three once, when setting a project up; after that only the right-hand half repeats — and it repeats identically on a laptop and in CI.

  1. 01 Installation brew · curl · npm
    → the speq binary     installer
  2. 02 speq init an empty repository
    → .speq/     kernel
  3. 03 speq install speq.yaml
    → ~/.speq + speq.lock     installer
  4. 04 Booting the kernel speq.lock, the environment
    → Registry     kernel
  5. 05 Discovery suites/*.yaml
    → TestDef[]     loader plugin
  6. 06 Validation TestDef[] + the grammar
    → Diagnostic[]     kernel plugin
  7. 07 Execution TestDef[]
    → events → RunOutcome     kernel plugin
How to read this

kernel is code in packages/core: the same for everyone, and knowing no protocol at all. plugin is code you can replace with your own without forking anything. installer is @speqkit/installer, a separate package: it works before the kernel has started at all.

The line runs more evenly than it looks: no stage is performed by a plugin in full. The kernel always keeps traversal, addressing and order; a plugin answers the question "what does this mean" at one particular point.

One command per stage

# once per machine
brew install speqkit

# once per project
speq init
speq add http yaml cli junit
speq install

# from then on, only this — locally and in CI
speq install --frozen
speq run --env ci --reporter console,junit
Stage 01 · before a run

Installation

What you install is speqkit; what you type is speq — the same split as @angular/cli and ng. There are three ways, and choosing between them comes down to exactly one thing: whether the repository has Node in it.

HowWhenWhat arrives
brew install speqkitmacOS, a repository in Go, Python, Java — anything at allOne executable with Node built into it
curl -fsSL … | shLinux, a CI image with no package managerThe same binary, without a package manager
npm i -g speqkitNode is already there and does not get in the wayA package from npm, with a speq bin

The binary is not a separate build of the kernel: scripts/verify-publish.mjs --binary points the same battery at it that the packages face, with an empty PATH. It has to install plugins from a registry and run a suite on a machine where node cannot be reached at all.

What that means for the repository

No node_modules, no package.json and in fact no Node artifact of any kind appears in the service's repository. What appears is a .speq/ directory and a speq.lock file — that is all. The plugins live in ~/.speq, shared across the machine.

Stage 02 · before a run

speq init

packages/core/src/bin.ts · commandInit

One of the few commands the kernel keeps for itself. The reason is simple: the rest come from the @speqkit/plugin-cli plugin, and there is nothing to install it with yet — speq.yaml does not exist.

speq init                      # the in-repo layout: everything goes into ./.speq/
speq init --mode test-repo     # a repository that is entirely about tests: everything at the root
.speq/
├── speq.yaml                  # the plugins and their settings
├── suites/
│   └── health.yaml            # the first test, and it works
├── environments/
│   ├── local.yaml             # speq run --env local
│   └── ci.yaml                # speq run --env ci
└── .gitignore                 # reports/ and links.yaml — not in git

Two layouts, not one:

  • in-repo — .speq/ inside the service's repository. The default: tests live next to the code they check.
  • test-repo — a repository with nothing in it but tests. That is where end-to-end suites go, the ones with no single owning service.

From then on the root is found by walking up the tree — the way git and cargo do — so speq run works from any subdirectory. The nearest root wins, so a project nested inside another project lives its own life. If both .speq/ and the directory itself look valid, the kernel refuses to guess and asks for --speq-root.

The test that is created straight away

# .speq/suites/health.yaml
name: service is up
tags: [smoke]

steps:
  - id: health
    type: http
    method: GET
    url: /health

assert:
  - type: status
    expected: 200

That is the whole test model: Suite → Test → Step → Assertion. A step with an id becomes addressable: whatever it returned is available further down as ${health.status}. The model is fixed in the kernel and is not extended by plugins — otherwise two users of one framework would write incompatible tests.

Stage 02 · before a run

Config and environments

packages/core/src/config.ts

speq.yaml answers exactly two questions: which plugins to load and how to configure them. A settings key is a plugin's short name, so @speqkit/plugin-http and speqkit-plugin-http both read the http block.

# .speq/speq.yaml
version: 1

extends: @acme/speq-preset          # optional

plugins:
  - yaml                          # a short name → @speqkit/plugin-yaml
  - http
  - cli
  - junit
  - speqkit-plugin-kafka          # somebody else's plugin — by its full name
  - github:acme/plugin-legacy#v2  # straight out of a repository

http:
  baseUrl: http://localhost:8080

extends: so that thirty services do not drift apart

A preset is an ordinary npm package with a speq.yaml of its own. A platform team publishes one set of plugins and raises its version in one place. Presets are applied first and the local file wins a conflict; a cycle in extends is an error rather than an endless walk.

An environment is a layer of settings. Settings only

# .speq/environments/ci.yaml — layered over speq.yaml
http:
  baseUrl: ${env:BASE_URL}
The prohibition that keeps --frozen honest

An environment cannot set plugins or extends — attempting it stops the run with an explanation. The plugin set is pinned by speq.lock, and speq install --frozen runs in CI before anyone has said which environment the run will use. An environment able to drag in a plugin would produce a lock that is correct for local and one package short for ci.

Config files expand ${env:NAME} and ${env:NAME:-fallback}. An unset variable with no fallback is an error rather than an empty string: otherwise the suite quietly aims at http:// and goes green against nothing.

${login.body.id}, meanwhile, is not touched in config at all. That syntax belongs to the run rather than to configuration, and it has to survive to execution verbatim.

An environment is chosen with the --env flag or the SPEQ_ENV variable. Which files ended up layered is always visible: speq doctor prints them as a list, nearest last.

Stage 03 · before a run

speq install

packages/installer/src/install.ts · store.ts · lock.ts

Our own installer, with no npm and no pnpm: HTTP to the registry, a hash check, extraction into ~/.speq, and speq.lock written. Exactly what a run needs is installed, and not one file lands in the service's repository.

What happens inside

  1. First pass — the presets. extends is read out of the local file without being unrolled: a preset is a package, and it has to be on disk before the config referring to it can be read.
  2. Second pass — the plugins. extends is now unrolled and the plugin list is known in full. Anything handed over by speq link is excluded from resolution.
  3. Resolving the graph. Version ranges become exact versions, the plugins' own dependencies included.
  4. Materialisation. The tarball is downloaded, the hash is checked, extraction goes into a temporary directory and is renamed atomically — an interrupted install cannot leave half a package behind for something later to treat as cached.
  5. Linking. Dependencies are laid out as symlinks inside the directory of the package that depends on them — pnpm's layout, for pnpm's reason: ordinary Node resolution walks real paths and finds them by itself, and two plugins with different versions of one library do not collide.
  6. The lock. speq.lock is written: the specifier as it was typed, the name, the exact version, the tarball's address, the hash, the dependencies.
~/.speq/store/
  @speqkit+plugin-http@0.1.0/
    node_modules/@speqkit/plugin-http/     # the package itself
                /semver -> ../../semver@7.6.3/...   # its dependency

The lock is the only thing committed

speq.lock exists for one guarantee: speq install --frozen in CI installs bit for bit what the developer installed. Without a lock, brew install speqkit cannot promise that, and plugin sets crawl apart across thirty repositories.

A plugin can arrive from somewhere other than a registry: github:acme/plugin#v2, git+ssh://…#main, a tarball by URL. A ref is resolved to a commit at install time, and what goes into the lock is the commit rather than the ref — otherwise --frozen in CI would install wherever the tag has moved since.

CommandWhat it does
speq installInstalls what speq.yaml asks for and updates the lock
speq install --frozenInstalls exactly the lock; any drift from the config is a failure. The CI mode
speq add http kafkaAppends to speq.yaml and installs immediately
speq remove kafkaRemoves it from the config. Deletes nothing from the store: that is shared and addressed by content
speq link ../my-pluginThe plugin you are writing right now. Beats both the store and node_modules
speq doctorNode, the store, the lock, the links, the environment, and what was loaded from where
Stage 04 · the run

Booting the kernel

packages/core/src/bootstrap.ts

Every command starts here except the ones that have to work before the plugins do. The whole kernel is these four steps; after them control goes outwards.

export async function bootstrap(options) {
  const root     = discoverRoot(options.root)        // find the project
  const config   = loadConfig(root.root, options)    // read the config
  const registry = await loadPlugins(config, root)  // load the plugins
  return { root, config, registry }                 // hand over control
}
  1. 1

    Where a plugin comes from kernel

    Four sources, in exactly this order:

    • path — an explicit ./ or / written straight into speq.yaml;
    • link — speq link, that is, the plugin being written right now; it beats everything;
    • store — ~/.speq, at the version in the lock. The ordinary case, and the only one in CI;
    • node_modules — ordinary Node resolution, for monorepos and Node projects.

    The store comes before node_modules, or the lock pins nothing. The fallback stays because the framework has to work in a repository that already is a Node project and never ran speq install. What came from where is shown by speq doctor — which warns when something arrived past the lock: "CI will not reproduce this".

    A short name is always a convenience and never a requirement. http is tried as @speqkit/plugin-http, then speqkit-plugin-http, then http. Somebody else's plugin needs nobody's blessing: it is named in full and it works.

  2. 2

    The compatibility check kernel

    The module's default export is taken, and it must have a setup(). Then the contract's major is compared:

    plugin '@speqkit/plugin-kafka' targets @speqkit/plugin-api v2,
this kernel speaks v1. Upgrade the plugin, or pin an older speq.

    The number comes from the copy of plugin-api the plugin was built against — definePlugin() stamps it in. Without that, a plugin that forgot its apiVersion would inherit the kernel's number and the check would be agreeing with itself.

    That is the whole agreement between a plugin and the kernel. A plugin does not know the kernel's version and does not need it — which is why a plugin's package.json does not mention the kernel in any form.

  3. 3

    setup(ctx): a plugin declares what it can do plugin

    Every plugin gets its own PluginContext and registers its contributions. A name already taken cannot be taken again — a second plugin declaring an http step stops the load and names whoever claimed it first. Nobody gets to silently override somebody else's step type.

    This is also where a plugin gets ctx.host — the running session: root, discover(), validate(), run(), runs(), replay(). The host is attached before the first setup(), so it can be used straight away.

    A plugin never imports the kernel. plugin-cli once began with import { bootstrap } from 'speqkit' — and that cost two things: the installer put a second copy of the kernel into the store, and the plugin called bootstrap() inside a process that had already booted. A test in the repository fails if any plugin's manifest mentions the kernel in anything a user would install.

  4. 4

    settle(): contributing to a surface that may not be there kernel

    Once every setup() has run, the kernel flushes the deferred injections — but only those whose services actually exist.

    ctx.inject(['cli'], ({ cli }) => {
  cli.register('coverage', { summary: '…', run })
})

    A plugin that wanted to add a command, in a session with no terminal surface, simply does not add it and stays fully usable. It behaves exactly the same inside VS Code, where nobody publishes cli.

    Which is also why speq run does not exist until @speqkit/plugin-cli is loaded: a command is a plugin's contribution too. The kernel keeps only init, install, add, remove, link, unlink, plugins, doctor, help and version — what you need in order to install the plugin that provides the rest.

Stage 05 · the run

Discovering the tests

packages/core/src/tests.ts · packages/plugin-yaml/src/index.ts

The kernel does not know what a test file is. It asks the loaders which extensions they claimed, walks suites/, and hands every matching file to whoever subscribed to it.

ctx.defineLoader('yaml', {
  extensions: ['.yaml', '.yml'],
  load(file, content) { return tests }   // TestDef[]
})

If there is no loader at all, the run stops immediately and says what is missing: "add a loader plugin (for YAML: @speqkit/plugin-yaml)". Finding no tests and being unable to read them are different troubles, and they must not be confused.

The YAML loader reads a file as a set of documents separated by ---, so any number of tests can live in one file. A test's default name is the file's name. The kernel adds a source to each: the path relative to the root, by which the test is later addressed from the CLI and grouped into a suite.

speq list                          # what is visible at all
speq run --test suites/health.yaml # one file
speq run --suite suites/smoke      # one directory
speq run --tags smoke,critical     # by tag
speq run --name 'menu.create[jpy]' # one test, cases included
speq run --shard 2/4               # this machine's quarter

The first four say which tests you care about and reach the loaders as a DiscoverQuery. --shard says the opposite — you care about all of them and there are four machines — so it is not a query at all: it is a contiguous slice of what discovery returned, applied last. The slice is by test rather than by file, because since cases a thousand tests in one file is a single test, and that is precisely the shape shards exist to split. Each shard is an independent run with its own events.jsonl and its own JUnit XML, and every suite that has work in it opens in it.

Why the format is a plugin

YAML ships in the box because it is read by people who do not program. A TypeScript loader is an ordinary plugin anyone can publish tomorrow without touching the kernel. defineLoader was laid down on day one for exactly that reason: adding it later would have meant the format had already become part of the kernel.

Stage 06 · the run

Checking before the first request

packages/core/src/validate.ts

Before every speq run — and on its own through speq validate — the tests are checked in full without touching a network. The kernel knows the entire grammar: which step and assertion types are registered, and which schema each declared for its inputs. A typo costs milliseconds instead of a half-finished run against a real environment.

What is looked at

  • the test has a name and at least one step;
  • step ids do not repeat;
  • the step type and the assertion type belong to somebody — otherwise a suggestion by Levenshtein distance: did you mean 'http'?;
  • required fields are present and there are no extra ones — if the schema closed itself;
  • and what a schema cannot say — the plugin's own check.

validate(): what a schema does not know

A schema answers for the shape of an input and nothing else. Whether the schema file an assertion refers to exists; whether such a topic is in the config; whether two mutually exclusive fields are both set — the plugin knows all of that and the schema does not.

ctx.defineStepType('loop', {
  schema: { /* the shape */ },

  validate(step) {
    const over = step.over !== undefined
    const times = step.times !== undefined
    if (over && times) return ["'over' and 'times' exclude each other"]
    if (!over && !times) return ["a loop needs 'over' or 'times'"]
    if (times && step.times <= 0) {
      return [{ path: 'times', code: 'not-positive', message: `'times' has to be positive` }]
    }
    return []
  },

  execute(exec, input) { /* … */ }
})

The kernel keeps traversal and addressing to itself. A plugin returns messages and at most a path inside its own step; steps[2].times and the file name are assembled by the kernel — so a plugin cannot lie about location, and a diagnostic with the wrong address is worse than none.

suites/smoke.yaml  steps[2]
  'over' and 'times' exclude each other; a loop is over a list or a count
suites/smoke.yaml  steps[4].times
  'times' has to be positive, got 0

2 problem(s)

The same answer, for something that is not a person

A generated suite is worth writing only if it can be checked before it runs, and until --json the only way to read the check was to match substrings of coloured stderr — so a reworded sentence silently changed what the caller concluded.

speq validate --json

{
  "checked": 12,
  "diagnostics": [
    {
      "file": "suites/smoke.yaml",
      "path": "steps[0].type",
      "code": "unknown-step-type",
      "message": "unknown step type 'htpp'",
      "hint": " — did you mean 'http'?"
    }
  ]
}

code is the field to switch on. The message is written for a person and may be reworded in any release; the code is written for a program and may not. The kernel's own are bare words — unknown-step-type, unknown-assertion, missing-field, unknown-field, duplicate-test-name — and anything a plugin's own validate found carries that plugin's short name in front of it, loop/not-positive, so the two sets can never collide.

run and list take --json too. The document goes to stdout even when the news is bad — run answers {"status": "invalid"} with the diagnostics rather than refusing in prose — and --json replaces the default reporter and not a chosen one, so --json --reporter junit still writes the XML.

Two rules of validation

It is synchronous. Every run waits for it, so it has to cost milliseconds: reading a file is allowed, going to the network is not.

A validator that throws is not a failed validation. An exception inside a plugin becomes a diagnostic about the plugin ("this is a bug in the plugin, not in the test"), and the other problems still reach the user. A bug in one plugin must not hide the very error the check was run for.

If there are diagnostics, speq run finishes with code 2 and runs nothing.

Stage 07 · the run

Execution

packages/core/src/runner.ts · executor.ts · resources.ts

From here everything is deterministic. The order below is exactly what runTests does, top to bottom.

  1. 1

    Reporters start before the first event

    The names in --reporter are resolved before the first test runs. A typo in a reporter's name is a configuration error, and finding out about it twenty minutes into a suite would be the worst possible moment.

    Separately and independently, the run log subscribes: events are written to reports/<runId>/events.jsonl line by line, whatever the reporters do afterwards, crashing included.

  2. 2

    The run scope opens kernel

    Resources live for one of three spans — run, suite, test — are taken lazily and closed in the reverse of the order they were taken. A browser is brought up once per run; a transaction lives for one test and is rolled back after it.

    ctx.defineResource('browser', {
  scope: 'run',
  setup: () => chromium.launch(),
  teardown: (b) => b.close()
})

    Scopes are a tree, not a stack: one run frame, a suite frame per suite, a test frame per test, each handed to whoever runs inside it. A lookup walks its own parents and reaches nothing a sibling owns, so data isolation under a parallel run falls out of the model rather than being bolted on later. The outer scopes close even if the test inside them blew up.

  3. 3

    Tests are grouped into suites, and suites are what run at once

    A file is the unit that runs: the grouping is over consecutive tests, so the order is never rearranged, and a suite scope opens and closes around it with a test scope around each test.

    Above that file are the suites it is in. A directory holding a suite.yaml is a suite, suites nest, and each one opens before the first test anywhere below it and closes after the last — running its own setup and cleanup once, in a scope the tests cannot read. Because the files under a suite go to whichever worker is free, the node counts what is left below it and whoever brings that count to zero closes it.

    speq run --workers 4 takes four suites at a time, from a shared queue: whoever finishes takes the next, so a suite that fails frees its slot instead of stopping the run. Concurrency is between suites and nowhere else. A test runs whole, interleaved with nothing; the tests inside one suite stay sequential, so a suite's hooks and its suite-scoped resources behave exactly as they did; and a step type that starts a second runSteps beside one still running is refused.

    One worker by default, and not as a placeholder. Every other runner defaults to the CPU count because its bottleneck is the local processor; speq's is somebody else's service, and four workers is four times the load on the system under test — enough for step timeouts to start firing where they did not fire in sequence. The number can change a verdict, so nothing guesses it and there is no auto.

  4. 4

    A step: preparing the input kernel

    id, type and timeout are taken off the step — those are the kernel's fields and the plugin does not receive them. A nested steps goes to the plugin untouched: the body of a loop has to be resolved afresh on every iteration, in a child scope the loop itself creates. Everything else is resolved:

    ${login.body.orderId}   // a path into step results and variables
${env:BASE_URL}         // a value provider, by prefix

    Providers may not answer immediately — a secret from a vault, a row from a database. All of one step's keys go to the providers at once and are awaited together; a provider is asked once per pass rather than once per mention. The wait happens under the step's timeout: a provider that went to the network and never came back is a step taking too long, not a hung run.

    A string that is entirely a template keeps the value's type: ${l.iterations} is the number 2, not the string "2".

  5. 5

    A step: execution plugin

    The time budget: the step's timeout, else the step type's timeoutMs, else 30 seconds. Cancellation reaches the plugin as exec.signal — an ordinary AbortSignal, passed to fetch or anywhere else.

    async execute(exec, input) {
  const { baseUrl } = exec.config()          // its own block from speq.yaml
  const res = await fetch(url, { signal: exec.signal })
  exec.attach('response.json', body, 'application/json')
  return { status: res.status, body }      // binds to the step's id
}

    What is returned is bound to the step's id and becomes addressable: ${health.status}. The step:before and step:after hooks fire around the step; a hook that throws becomes a warning in the event stream and does not bring the run down.

    A crash inside a plugin is an error, not a failed. The test did not prove the system wrong; it failed to ask the question. The difference shows in the report and in the exit code, and confusing them means showing a broken environment as a discovered bug.

  6. 6

    Nested steps: why a loop is a plugin plugin

    The executor is re-entrant and handed to plugins as exec.runSteps. From these three lines follow loop, retry, if and try/catch — there is not one control construct in the kernel, and there will never need to be. One call at a time, though: a step type that starts a second runSteps beside one still running is refused, because a test is the unit speq runs atomically.

    for (const [index, item] of items.entries()) {
  const records = await exec.runSteps(children, {
    vars: { [alias]: item, [`${alias}Index`]: index },
    label: `${alias}=${short(item)}`
  })
}

    A nested call gets a child variable frame, and that frame does not leak outwards: ${item} after the loop is an error, "'item' is not defined", rather than a last value quietly picked up.

  7. 7

    Assertions plugin

    Assertions are evaluated only if no step ended in error. Checking anything after a broken step is printing noise instead of evidence.

    An assertion sees results — every step result by its id — and last, the result of the final step, which is what an assertion with no explicit address refers to. An assertion's input is resolved by the same pass as a step's, so expected: ${greeting.message} works exactly as written in the file.

    A failing assertion is failed: the test did its job and found a discrepancy. An exception thrown inside an assertion is a failure carrying the error's text, not a collapsed run.

  8. 8

    The verdict of a test and of a run kernel

    Status is assembled bottom-up, with no exceptions to the rule: any error → error; otherwise any failing assertion or failed step → failed; otherwise passed.

Stage 07 · the run

Report, artifacts and the exit code

packages/core/src/reporters.ts · artifacts.ts · run-log.ts

The event stream is the only report contract

Everything visible from outside a run is eleven event types. The terminal, JUnit, the TUI, a VS Code panel and an external collector all read the same stream; the kernel does not know any of them exist.

run.started → suite.started → suite.started (parent named)
                → step.started → step.finished   (the suite's own setup)
                → test.started
                  → step.started → step.finished
                  → artifact.attached
                  → assertion.evaluated
                test.finished
              suite.finished → suite.finished → run.finished
                                          diagnostic (at any moment)

A step, an assertion or an artifact names exactly one of test and suite: the second is work that belongs to no test, because a suite exists before the first one and after the last. A reporter that only knows about tests asks for test and skips the rest.

A reporter is a function of that stream and nothing else:

ctx.defineReporter('console', {
  init(ctx) { /* runId, and where it may write */ },
  on(event) { /* every event of the run */ },
  finalize() { /* finish the file */ }
})

A reporter that breaks does not bring the run down — the exception is printed and things carry on. Terminal output is not an exception to the mechanism but an ordinary reporter named console, on by default: an extension point nobody walks does not work.

Artifacts

exec.attach(name, body, contentType) puts a file into the report: the body is written to reports/<runId>/artifacts/<test>/ and the event carries the size and the path. Two screenshots with the same name in one test are two files, not one. When there is no report directory (a library call, a unit test) the bodies stay in memory and are available in the run's outcome.

speq report: the same report, without running anything again

speq report --list                    # which runs are recorded
speq report                           # redraw the latest
speq report --run 3f2a --reporter junit

The events are read back out of the log and fed into the same bus. A reporter cannot tell a replay from a live run — and should not be able to. That is what keeps the claim "the event stream is enough to build a report" checkable: a test in the repository demands that a replay produce a byte-for-byte identical file to watching it live.

Your own plugin

From nothing in five minutes

You write a plugin when the thing you need does not exist — a MongoDB client, your own report format, your own schema validation, your own way of keeping variables between tests. None of it has to be agreed with anyone, and the kernel is not forked for it.

npm create speqkit-plugin kafka
cd speqkit-plugin-kafka
npm install && npm test
speqkit-plugin-kafka/
├── package.json        # the contract as a peer; no kernel among the dependencies
├── src/index.ts        # a step type and an assertion, both with schemas
├── test/plugin.test.ts # eight tests against the real kernel
├── vitest.config.ts
├── tsconfig.json
└── README.md

The generator makes the decisions that are easiest to get wrong: the contract is declared a peer dependency rather than an ordinary one; the kernel is mentioned nowhere; the step and the assertion carry schemas; and the speqkit-plugin keyword is in place — that is how a plugin is found.

The one real rule

A plugin never imports speqkit. It runs inside a kernel that is already up, and everything it needs arrives in ctx. A plugin that names the kernel among its dependencies puts a second copy of the kernel into the user's store and starts it. We made that mistake once, in our own plugin-cli; the template is where it stopped being inherited.

The eight contribution points

Every point that is opened becomes a contract forever — it cannot be closed again. Eight are enough to write http, playwright, postgres, loop, tui and vscode.

  • defineStepTypeWhat a test can do. An input schema, an optional validate, execute(exec, input) → a result bound to an id
  • defineAssertionWhat a test can check. Sees the step results and the last of them
  • defineResourceAn object living for run | suite | test: a browser, a connection pool, a transaction
  • defineReporterA function of the event stream. JUnit, Allure, your own collector
  • defineValueProviderYour own prefix in ${...}: env, vault, faker. It may answer asynchronously
  • defineLoaderThe format of a test file. YAML is a plugin like any other
  • defineHookrun, suite, test, step — before and after each
  • provide / injectA service for other plugins, and a contribution to a surface that may not be there
The grammar is readable from outside

Everything registered above — every step type, assertion, value provider, reporter and loader, with the schema each declared — comes back from ctx.host.capabilities(), and from speq capabilities --json for anyone who is not a plugin. It had been in the registry since load and had never left it, so an editor offering completion, a palette in a panel and a system prompt describing speq to a model each carried their own copy of the vocabulary — one that goes stale the moment somebody installs a plugin, and goes stale silently, because a suite written against the wrong vocabulary looks exactly like a suite with a typo in it.

And what any of it is for

The grammar says what may be written and never what it means. That half lived in a README on a website — a document a session cannot ask, cannot check, and which is wrong the moment somebody renames a step type. So a plugin declares it: docs on definePlugin carries a summary, a link and examples, each naming with for the capabilities it demonstrates, and every contribution def carries a one-line summary. speq docs kafka answers out of that, and speq docs --json hands a model the vocabulary and a working line of each in one call.

speq docs --check is the part that keeps it true: an example naming a step type that no longer exists is an error, because that is exactly what a rename leaves behind. It is optional on the type — a fixture plugin declared inside a test has no documentation and should not have to pretend otherwise — and required by check-plugin-package.mjs, which is where a package meets a registry.

Plus what ctx gives without being a contribution point

  • ctx.config()Its own block in speq.yaml, already checked against configSchema. The key is the plugin's short name
  • ctx.hostThe running session: root, reportDir, env, discover(), validate(), run(), runs(), replay(), capabilities()
  • ctx.onEventA subscription to the run's event stream

What a minimal plugin looks like in full

import { definePlugin } from '@speqkit/plugin-api'

export default definePlugin({
  name: 'speqkit-plugin-kafka',

  // This plugin's block in speq.yaml, under the key `kafka`.
  configSchema: {
    type: 'object',
    properties: { brokers: { type: 'array' } }
  },

  setup(ctx) {
    ctx.defineStepType('kafka.publish', {
      schema: {
        type: 'object',
        properties: { topic: { type: 'string' }, message: {} },
        required: ['topic'],
        additionalProperties: false
      },

      validate(step) {
        return String(step.topic).trim() === ''
          ? [{ path: 'topic', message: "'topic' is empty" }]
          : []
      },

      async execute(exec, input) {
        const producer = await exec.resource('kafka.producer')
        const { offset } = await producer.send(input)
        return { offset }        // → ${publish.offset}
      }
    })
  }
})

Testing a plugin: the real kernel, no fakes

@speqkit/test-kit assembles the real Registry, Executor and runner — the same ones speq run uses. A mock ExecContext would be a second implementation of the contract, written by us and drifting from the first, and all it would prove is that the plugin agrees with our mock.

const kit = await harness(plugin, { config: { kafka: { brokers: [] } } })

const step = await kit.step({ type: 'kafka.publish', topic: 'orders' })
expect(step.result.offset).toBe(0)

// and the diagnostics a bad test would produce
expect(kit.validate([{ name: 't', source: 'a.yaml',
  steps: [{ type: 'kafka.publish', topic: '  ' }] }]))
  .toEqual([{ file: 'a.yaml', path: 'steps[0].topic', message: "'topic' is empty" }])

await kit.close()

The kit adds exactly two things to the kernel that a plugin author does not otherwise have: a project root on disk, and a scope stack held open between calls — so that ${id.field} works the way it does in a test file. A green test here means the plugin works in a project.

Debugging against a live project

cd ../my-service/.speq
speq link ../../speqkit-plugin-kafka   # beats the store and node_modules
speq plugins                           # what is loaded and what it gave
speq capabilities                      # the grammar, yours included
speq docs kafka                        # what you said it is for, and your examples
speq docs --check                      # an example naming something that moved
speq run --test suites/orders.yaml
speq unlink speqkit-plugin-kafka

Publishing

npm publish                 # --access public for a scope

After that the plugin installs like any other — speq add speqkit-plugin-kafka. A short name such as kafka is tried as @speqkit/plugin-kafka first, but a package named in full installs as written. Nobody's permission is needed for any of it.

Compatibility

A plugin and the kernel agree on one thing: the major of @speqkit/plugin-api. While it is 1, a plugin built today will load into a kernel released later. An addition to the contract is a minor version and a change or removal is a major; before 1.0 the contract may change, and the package's README says so plainly.

This document describes speqkit 0.4.0 and the @speqkit/plugin-api 0.11.0 contract (PLUGIN_API_VERSION = 1), as of 3 September 2026. Every stage is named by the file it lives in, so the code can be read alongside. The architectural decisions and their reasons are covered separately, in "The speqkit plugin framework".
