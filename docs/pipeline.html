Обзор

Карта пайплайна

Семь стадий. Первые три вы проходите один раз при заведении проекта, дальше повторяется только правая половина — и повторяется одинаково на ноутбуке и в CI.

  1. 01 Установка brew · curl · npm
    → бинарь speq     установщик
  2. 02 speq init пустой репозиторий
    → .speq/     ядро
  3. 03 speq install speq.yaml
    → ~/.speq + speq.lock     установщик
  4. 04 Загрузка ядра speq.lock, окружение
    → Registry     ядро
  5. 05 Обнаружение suites/*.yaml
    → TestDef[]     плагин-загрузчик
  6. 06 Проверка TestDef[] + грамматика
    → Diagnostic[]     ядро плагин
  7. 07 Исполнение TestDef[]
    → события → RunOutcome     ядро плагин
Как это читать

ядро — код в packages/core, он одинаков у всех и не знает ни одного протокола. плагин — код, который можно заменить своим, ничего не форкая. установщик — @speqkit/installer, отдельный пакет: он работает до того, как ядро вообще запустилось.

Граница проходит ровнее, чем кажется: ни одна стадия не выполняется плагином целиком. Ядро всегда держит обход, адресацию и порядок; плагин отвечает на вопрос «что это значит» в конкретной точке.

Одной командой на каждую стадию

# один раз на машину
brew install speqkit

# один раз на проект
speq init
speq add http yaml cli junit
speq install

# дальше — только это, локально и в CI
speq install --frozen
speq run --env ci --reporter console,junit
Стадия 01 · до прогона

Установка

Устанавливается speqkit, набирается speq — тот же раскол, что у @angular/cli и ng. Три способа, и выбор между ними определяется ровно одним: есть ли в репозитории Node.

СпособКогдаЧто приезжает
brew install speqkitmacOS, репозиторий на Go, Python, Java — где угодноОдин исполняемый файл с вшитым внутрь Node
curl -fsSL … | shLinux, CI-образ без пакетного менеджераТот же бинарь, без пакетного менеджера
npm i -g speqkitNode уже стоит и это не мешаетПакет из npm, бин speq

Бинарник — не отдельная сборка ядра: scripts/verify-publish.mjs --binary прогоняет по нему ту же батарею, что и по пакетам, с пустым PATH. Он обязан поставить плагины из реестра и прогнать набор на машине, где до node дотянуться нельзя вообще.

Что это значит для репозитория

В репозитории сервиса не появляется node_modules, package.json и вообще ни одного артефакта Node. Появляется каталог .speq/ и файл speq.lock — всё. Плагины лежат в ~/.speq, общем на всю машину.

Стадия 02 · до прогона

speq init

packages/core/src/bin.ts · commandInit

Одна из немногих команд, которые ядро держит у себя. Причина простая: остальные приходят из плагина @speqkit/plugin-cli, а его ещё нечем поставить — speq.yaml не существует.

speq init                      # раскладка in-repo: всё уезжает в ./.speq/
speq init --mode test-repo     # репозиторий целиком про тесты: всё в корень
.speq/
├── speq.yaml                  # плагины и их настройки
├── suites/
│   └── health.yaml            # первый тест, рабочий
├── environments/
│   ├── local.yaml             # speq run --env local
│   └── ci.yaml                # speq run --env ci
└── .gitignore                 # reports/ и links.yaml — не в git

Две раскладки, а не одна:

  • in-repo — .speq/ внутри репозитория сервиса. По умолчанию: тесты живут рядом с кодом, который проверяют.
  • test-repo — репозиторий, в котором нет ничего кроме тестов. Туда уезжают сквозные наборы, у которых нет одного сервиса-владельца.

Дальше корень ищется подъёмом вверх по дереву — как это делают git и cargo, — так что speq run работает из любой подпапки. Ближайший корень выигрывает, поэтому проект, вложенный в другой проект, живёт своей жизнью. Если и .speq/, и сам каталог выглядят валидными, ядро отказывается угадывать и просит --speq-root.

Тест, который создаётся сразу

# .speq/suites/health.yaml
name: service is up
tags: [smoke]

steps:
  - id: health
    type: http
    method: GET
    url: /health

assert:
  - type: status
    expected: 200

Это и есть вся тестовая модель: Suite → Test → Step → Assertion. Шаг с id становится адресуемым: то, что он вернул, доступно дальше как ${health.status}. Модель зафиксирована в ядре и не расширяется плагинами — иначе два пользователя одного фреймворка писали бы несовместимые тесты.

Стадия 02 · до прогона

Конфиг и окружения

packages/core/src/config.ts

speq.yaml отвечает ровно на два вопроса: какие плагины загрузить и как их настроить. Ключ настройки — короткое имя плагина, поэтому @speqkit/plugin-http и speqkit-plugin-http оба читают блок http.

# .speq/speq.yaml
version: 1

extends: @acme/speq-preset          # необязательно

plugins:
  - yaml                          # короткое имя → @speqkit/plugin-yaml
  - http
  - cli
  - junit
  - speqkit-plugin-kafka          # чужой плагин — полным именем
  - github:acme/plugin-legacy#v2  # прямо из репозитория

http:
  baseUrl: http://localhost:8080

extends: чтобы тридцать сервисов не разъехались

Пресет — обычный npm-пакет со своим speq.yaml. Платформенная команда публикует один набор плагинов и поднимает его версию в одном месте. Пресеты применяются первыми, локальный файл выигрывает при конфликте; цикл в extends — ошибка, а не бесконечный обход.

Окружение — это слой настроек. И только настроек

# .speq/environments/ci.yaml — накладывается поверх speq.yaml
http:
  baseUrl: ${env:BASE_URL}
Запрет, который держит --frozen честным

Окружение не может задать plugins или extends — попытка это сделать останавливает запуск с объяснением. Набор плагинов пинится speq.lock, а speq install --frozen отрабатывает в CI раньше, чем кто-либо сказал, какое окружение возьмёт прогон. Окружение, умеющее втащить плагин, породило бы лок, верный для local и неполный на один пакет для ci.

В конфигах раскрывается ${env:NAME} и ${env:NAME:-fallback}. Незаданная переменная без запасного значения — ошибка, а не пустая строка: иначе набор молча целится в http:// и зеленеет против ничего.

При этом ${login.body.id} в конфиге не трогается вовсе. Этот синтаксис принадлежит прогону, а не конфигурации, и обязан дожить до исполнения дословно.

Окружение выбирается флагом --env или переменной SPEQ_ENV. Какие файлы в итоге сложились, всегда видно: speq doctor печатает их списком, ближайший последним.

Стадия 03 · до прогона

speq install

packages/installer/src/install.ts · store.ts · lock.ts

Свой установщик, без npm и pnpm: HTTP к реестру, проверка хеша, распаковка в ~/.speq, запись speq.lock. Ставится ровно то, что нужно для прогона, и ни одного файла в репозитории сервиса.

Что происходит внутри

  1. Проход первый — пресеты. extends читается из локального файла без разворачивания: пресет это пакет, и он обязан оказаться на диске раньше, чем можно прочитать конфиг, который на него ссылается.
  2. Проход второй — плагины. Теперь extends развёрнут, список плагинов известен целиком. Всё, что отдано через speq link, из резолва исключается.
  3. Резолв графа. Диапазоны версий превращаются в точные версии, включая зависимости самих плагинов.
  4. Материализация. Тарбол скачивается, хеш сверяется, распаковка идёт во временный каталог и переименовывается атомарно — прерванная установка не может оставить полупакет, который потом сочтут закешированным.
  5. Линковка. Зависимости раскладываются симлинками внутрь каталога зависящего пакета — раскладка pnpm, и по той же причине: обычный резолв Node ходит по реальным путям и находит их сам, а два плагина с разными версиями одной библиотеки не конфликтуют.
  6. Лок. Пишется speq.lock: спецификация как её написали, имя, точная версия, адрес тарбола, хеш, зависимости.
~/.speq/store/
  @speqkit+plugin-http@0.1.0/
    node_modules/@speqkit/plugin-http/     # сам пакет
                /semver -> ../../semver@7.6.3/...   # его зависимость

Лок — единственное, что коммитится

speq.lock существует ради одной гарантии: speq install --frozen в CI ставит бит-в-бит то же, что поставил разработчик. Без лока brew install speqkit такого пообещать не может, и наборы плагинов расползаются по тридцати репозиториям.

Плагин может приехать не только из реестра: github:acme/plugin#v2, git+ssh://…#main, тарбол по URL. Ref при установке разрешается в коммит, и в лок попадает коммит, а не ref — иначе --frozen в CI ставил бы то, куда с тех пор переехал тег.

КомандаЧто делает
speq installСтавит то, что просит speq.yaml, и обновляет лок
speq install --frozenСтавит ровно лок; расхождение с конфигом — падение. Режим CI
speq add http kafkaДописывает в speq.yaml и сразу ставит
speq remove kafkaУбирает из конфига. Из стора не удаляет ничего: он общий и адресуется содержимым
speq link ../my-pluginПлагин, который вы прямо сейчас пишете. Выигрывает и у стора, и у node_modules
speq doctorNode, стор, лок, линки, окружение, что откуда загрузилось
Стадия 04 · прогон

Загрузка ядра

packages/core/src/bootstrap.ts

Отсюда начинается любая команда, кроме тех, что обязаны работать до плагинов. Всё ядро — вот эти четыре шага; дальше управление уходит наружу.

export async function bootstrap(options) {
  const root     = discoverRoot(options.root)        // найти проект
  const config   = loadConfig(root.root, options)    // прочитать конфиг
  const registry = await loadPlugins(config, root)  // загрузить плагины
  return { root, config, registry }                 // отдать управление
}
  1. 1

    Откуда берётся плагин ядро

    Четыре источника, ровно в этом порядке:

    • path — явный ./ или / прямо в speq.yaml;
    • link — speq link, то есть плагин, который пишут прямо сейчас; он выигрывает у всего;
    • store — ~/.speq, по версии из лока. Обычный случай и единственный в CI;
    • node_modules — обычный резолв Node, для монореп и Node-проектов.

    Стор стоит перед node_modules, иначе лок ничего не пинит. Запасной вариант остаётся, потому что фреймворк обязан работать в репозитории, который уже является Node-проектом и speq install не запускал. Что откуда пришло, показывает speq doctor — и предупреждает, если что-то приехало мимо лока: «CI это не воспроизведёт».

    Короткое имя — всегда удобство, никогда требование. http проверяется как @speqkit/plugin-http, затем speqkit-plugin-http, затем http. Чужому плагину не нужно ничьё благословение: он называется полным именем и работает.

  2. 2

    Проверка совместимости ядро

    У модуля берётся default-экспорт, и он обязан иметь setup(). Дальше сверяется мажор контракта:

    plugin '@speqkit/plugin-kafka' targets @speqkit/plugin-api v2,
this kernel speaks v1. Upgrade the plugin, or pin an older speq.

    Число берётся из той копии plugin-api, с которой плагин собран, — её проставляет definePlugin(). Без этого плагин, забывший apiVersion, унаследовал бы число ядра, и проверка согласилась бы сама с собой.

    Это вся договорённость между плагином и ядром. Версия ядра плагину неизвестна и не нужна — поэтому в package.json плагина ядра нет ни в каком виде.

  3. 3

    setup(ctx): плагин заявляет, что умеет плагин

    Каждый плагин получает свой PluginContext и регистрирует вклады. Занять уже занятое имя нельзя — второй плагин, объявивший шаг http, останавливает загрузку с указанием, кто занял его первым. Молча переопределять чужой тип шага не даёт никто.

    Здесь же плагин получает ctx.host — работающую сессию: root, discover(), validate(), run(), runs(), replay(). Хост прикручен до первого setup(), так что им можно пользоваться сразу.

    Плагин никогда не импортирует ядро. Когда-то plugin-cli начинался с import { bootstrap } from 'speqkit' — и это стоило двух вещей: установщик клал в стор вторую копию ядра, а плагин вызывал bootstrap() внутри процесса, который уже загрузился. Тест в репозитории падает, если хоть один манифест плагина упомянет ядро в том, что ставит себе пользователь.

  4. 4

    settle(): вклад в поверхность, которой может не быть ядро

    Когда все setup() отработали, ядро проливает отложенные инъекции — но только те, чьи сервисы действительно есть.

    ctx.inject(['cli'], ({ cli }) => {
  cli.register('coverage', { summary: '…', run })
})

    Плагин, который хотел дописать команду, а терминальной поверхности в этой сессии нет — просто не дописывает её и остаётся полностью рабочим. Ровно так же он ведёт себя внутри VS Code, где cli никто не публикует.

    Поэтому speq run и не существует, пока не загружен @speqkit/plugin-cli: команда — это тоже вклад плагина. Ядро держит у себя только init, install, add, remove, link, unlink, plugins, doctor, help, version — то, без чего нечем поставить плагин, дающий остальное.

Стадия 05 · прогон

Обнаружение тестов

packages/core/src/tests.ts · packages/plugin-yaml/src/index.ts

Ядро не знает, что такое файл теста. Оно спрашивает загрузчики, какие расширения они забрали, обходит suites/ и отдаёт каждый подходящий файл тому, кто на него подписался.

ctx.defineLoader('yaml', {
  extensions: ['.yaml', '.yml'],
  load(file, content) { return tests }   // TestDef[]
})

Если загрузчика нет ни одного, прогон останавливается сразу и говорит, чего не хватает: «add a loader plugin (for YAML: @speqkit/plugin-yaml)». Не найти ни одного теста и не уметь их читать — разные беды, и путать их нельзя.

YAML-загрузчик читает файл как набор документов, разделённых ---, так что в одном файле живёт сколько угодно тестов. Имя теста по умолчанию — имя файла. Ядро дописывает каждому source: путь относительно корня, по которому тест потом адресуется из CLI и группируется в набор.

speq list                          # что вообще видно
speq run --test suites/health.yaml # один файл
speq run --suite suites/smoke      # один каталог
speq run --tags smoke,critical     # по тегам
Почему формат — плагин

YAML едет в коробке, потому что его читают люди, которые не программируют. Загрузчик на TypeScript — обычный плагин, который кто угодно опубликует завтра, не трогая ядро. Точка defineLoader заложена с первого дня именно ради этого: дописать её потом означало бы, что формат успел стать частью ядра.

Стадия 06 · прогон

Проверка до первого запроса

packages/core/src/validate.ts

Перед каждым speq run — и отдельно по speq validate — тесты проверяются целиком, не сходив ни в одну сеть. Ядро знает всю грамматику: какие типы шагов и ассертов зарегистрированы и какую схему каждый объявил для своих входов. Опечатка стоит миллисекунды вместо наполовину прошедшего прогона против настоящего окружения.

Что смотрится

  • у теста есть имя и хотя бы один шаг;
  • id шагов не повторяются;
  • тип шага и тип ассерта кому-то принадлежат — иначе подсказка по расстоянию Левенштейна: did you mean 'http'?;
  • обязательные поля на месте, лишних нет — если схема себя закрыла;
  • и то, что схема сказать не может, — собственная проверка плагина.

validate(): то, чего схема не знает

Схема отвечает за форму входа и только за неё. Существует ли файл схемы, на который ссылается ассерт; есть ли такой топик в конфиге; не заданы ли разом два взаимоисключающих поля — всё это плагин знает, а схема нет.

ctx.defineStepType('loop', {
  schema: { /* форма */ },

  validate(step) {
    const over = step.over !== undefined
    const times = step.times !== undefined
    if (over && times) return ["'over' and 'times' exclude each other"]
    if (!over && !times) return ["a loop needs 'over' or 'times'"]
    if (times && step.times <= 0) {
      return [{ path: 'times', message: `'times' has to be positive` }]
    }
    return []
  },

  execute(exec, input) { /* … */ }
})

Обход дерева и адресацию ядро оставляет себе. Плагин возвращает сообщения и максимум путь внутри своего шага; steps[2].times и имя файла собирает ядро — соврать про место плагин не может, а диагностика с неправильным адресом вреднее отсутствующей.

suites/smoke.yaml  steps[2]
  'over' and 'times' exclude each other; a loop is over a list or a count
suites/smoke.yaml  steps[4].times
  'times' has to be positive, got 0

2 problem(s)
Два правила проверки

Она синхронная. Прогон ждёт её каждый раз, и стоить она обязана миллисекунды: прочитать файл можно, сходить по сети — нет.

Упавший валидатор — не падение проверки. Исключение внутри плагина становится диагностикой про плагин («this is a bug in the plugin, not in the test»), а остальные проблемы всё равно доезжают до пользователя. Баг в одном плагине не должен прятать ту ошибку, ради которой проверку и запускали.

Если диагностики есть, speq run заканчивается кодом 2 и не запускает ничего.

Стадия 07 · прогон

Исполнение

packages/core/src/runner.ts · executor.ts · resources.ts

Дальше всё детерминировано. Порядок ниже — ровно то, что делает runTests, сверху вниз.

  1. 1

    Репортеры стартуют раньше первого события

    Имена из --reporter резолвятся до того, как побежал первый тест. Опечатка в имени репортера — ошибка конфигурации, и узнать о ней через двадцать минут после начала набора было бы худшим из возможных моментов.

    Отдельно и независимо подписывается журнал прогона: события пишутся в reports/<runId>/events.jsonl построчно, что бы репортеры дальше ни делали, включая падение.

  2. 2

    Открывается скоуп run ядро

    Ресурсы живут в трёх сроках — run, suite, test, — берутся лениво и закрываются в порядке, обратном взятию. Браузер поднимается один раз на прогон; транзакция живёт один тест и откатывается после него.

    ctx.defineResource('browser', {
  scope: 'run',
  setup: () => chromium.launch(),
  teardown: (b) => b.close()
})

    Изоляция данных при параллельном прогоне выпадает отсюда сама, а не прикручивается потом. Внешние скоупы закрываются, даже если тест внутри взорвался.

  3. 3

    Тесты группируются в наборы

    Набор — это файл-источник, группировка идёт по подряд идущим тестам, так что порядок не переставляется никогда. Вокруг каждого набора открывается и закрывается скоуп suite, вокруг каждого теста — test.

  4. 4

    Шаг: подготовка входа ядро

    С шага снимается id, type и timeout — это поля ядра, плагин их не получает. Вложенный steps уходит плагину нетронутым: тело цикла обязано резолвиться заново на каждой итерации, в дочернем скоупе, который создаёт сам цикл. Всё остальное резолвится:

    ${login.body.orderId}   // путь в результаты шагов и переменные
${env:BASE_URL}         // провайдер значений, по префиксу

    Провайдеры могут отвечать не сразу — секрет из vault'а, строка из базы. Все ключи одного шага уходят к провайдерам одновременно и ожидаются разом; провайдера спрашивают один раз на проход, а не на каждое упоминание. Ожидание идёт под таймаутом шага: провайдер, ушедший в сеть и не вернувшийся, — это шаг, который слишком долго идёт, а не повисший прогон.

    Строка, которая целиком является шаблоном, сохраняет тип значения: ${l.iterations} — это число 2, а не строка «2».

  5. 5

    Шаг: исполнение плагин

    Бюджет времени: timeout шага, иначе timeoutMs типа шага, иначе 30 секунд. Отмена приходит плагину как exec.signal — обычный AbortSignal, который передают в fetch и куда угодно ещё.

    async execute(exec, input) {
  const { baseUrl } = exec.config()          // свой блок из speq.yaml
  const res = await fetch(url, { signal: exec.signal })
  exec.attach('response.json', body, 'application/json')
  return { status: res.status, body }      // привяжется к id шага
}

    Возвращённое связывается с id шага и становится адресуемым: ${health.status}. Вокруг шага стреляют хуки step:before и step:after; упавший хук становится предупреждением в потоке событий и прогон не роняет.

    Падение внутри плагина — это error, а не failed. Тест не доказал, что система неправа; он не сумел задать вопрос. Разница видна в отчёте и в коде выхода, и путать их — значит показывать сломанный стенд как найденный баг.

  6. 6

    Вложенные шаги: почему цикл — плагин плагин

    Исполнитель реентрантный и отдан плагинам как exec.runSteps. Из этих трёх строк следуют loop, retry, parallel, if и try/catch — ни одной управляющей конструкции в ядре нет и не потребуется.

    for (const [index, item] of items.entries()) {
  const records = await exec.runSteps(children, {
    vars: { [alias]: item, [`${alias}Index`]: index },
    label: `${alias}=${short(item)}`
  })
}

    Вложенный вызов получает дочерний кадр переменных, и наружу этот кадр не протекает: ${item} после цикла — ошибка «'item' is not defined», а не тихо подхваченное последнее значение.

  7. 7

    Ассерты плагин

    Ассерты считаются, только если ни один шаг не завершился error. Проверять что-то после сломавшегося шага — печатать шум вместо улик.

    Ассерт видит results — все результаты шагов по их id — и last, результат последнего шага, к которому относится ассерт без явного адреса. Вход ассерта резолвится тем же проходом, что и вход шага, поэтому expected: ${greeting.message} работает ровно так, как написано в файле.

    Упавший ассерт — это failed: тест сделал свою работу и нашёл расхождение. Брошенное исключение внутри ассерта — это провал с текстом ошибки, а не падение прогона.

  8. 8

    Итог теста и прогона ядро

    Статус собирается снизу вверх, без исключений из правила: хоть один error → error; иначе хоть один непрошедший ассерт или упавший шаг → failed; иначе passed.

Поток событий — единственный контракт отчёта

Всё, что видно снаружи прогона, — это одиннадцать типов событий. Терминал, JUnit, TUI, панель VS Code и внешний коллектор читают один и тот же поток; ядро не знает, что кто-то из них существует.

run.started → suite.started → test.started
                → step.started → step.finished
                → artifact.attached
                → assertion.evaluated
              test.finished  → suite.finished → run.finished
                                          diagnostic (в любой момент)

Репортер — функция от этого потока, и ничего больше:

ctx.defineReporter('console', {
  init(ctx) { /* runId, куда можно писать */ },
  on(event) { /* каждое событие прогона */ },
  finalize() { /* дописать файл */ }
})

Сломавшийся репортер не роняет прогон — исключение печатается и идёт дальше. Терминальный вывод не исключение из механизма, а обычный репортер по имени console, включённый по умолчанию: точка расширения, по которой никто не ходит, не работает.

Артефакты

exec.attach(name, body, contentType) кладёт файл в отчёт: тело пишется в reports/<runId>/artifacts/<тест>/, а событие несёт размер и путь. Два скриншота с одним именем в одном тесте — два файла, а не один. Когда каталога отчётов нет (библиотечный вызов, юнит-тест), тела остаются в памяти и доступны в исходе прогона.

speq report: тот же отчёт, без повторного прогона

speq report --list                    # какие прогоны записаны
speq report                           # перерисовать последний
speq report --run 3f2a --reporter junit

События перечитываются из журнала и подаются на ту же шину. Репортер не может отличить повтор от живого прогона — и не должен. Это и держит утверждение «поток событий достаточен для отчёта» проверяемым: тест в репозитории требует, чтобы повтор давал байт-в-байт тот же файл, что и наблюдение вживую.

Свой плагин

С нуля за пять минут

Плагин пишется, когда нужного нет — клиент MongoDB, свой формат отчёта, своя валидация по схемам, свой способ хранить переменные между тестами. Согласовывать это ни с кем не нужно, и ядро для этого не форкается.

npm create speqkit-plugin kafka
cd speqkit-plugin-kafka
npm install && npm test
speqkit-plugin-kafka/
├── package.json        # контракт в peer; ядра нет в зависимостях
├── src/index.ts        # тип шага и ассерт, оба со схемами
├── test/plugin.test.ts # восемь тестов против настоящего ядра
├── vitest.config.ts
├── tsconfig.json
└── README.md

Генератор принимает решения, которые легче всего принять неправильно: контракт объявлен peer-зависимостью, а не обычной; ядро не упомянуто нигде; у шага и ассерта есть схемы; keyword speqkit-plugin на месте — по нему плагин находят.

Единственное настоящее правило

Плагин никогда не импортирует speqkit. Он исполняется внутри уже запущенного ядра, и всё, что ему нужно, приезжает в ctx. Плагин, назвавший ядро в зависимостях, кладёт в стор пользователя вторую копию ядра и запускает её. Мы совершили эту ошибку один раз, в собственном plugin-cli; шаблон — то место, где она перестала наследоваться.

Восемь точек вклада

Каждая открытая точка становится контрактом навсегда — закрыть обратно нельзя. Восьми хватает, чтобы написать http, playwright, postgres, loop, tui и vscode.

  • defineStepTypeЧто тест умеет делать. Схема входа, необязательный validate, execute(exec, input) → результат, привязываемый к id
  • defineAssertionЧто тест умеет проверять. Видит результаты шагов и последний из них
  • defineResourceОбъект со сроком жизни run | suite | test: браузер, пул соединений, транзакция
  • defineReporterФункция от потока событий. JUnit, Allure, свой коллектор
  • defineValueProviderСвой префикс в ${...}: env, vault, faker. Можно отвечать асинхронно
  • defineLoaderФормат файла тестов. YAML — такой же плагин, как и любой другой
  • defineHookrun, suite, test, step — до и после каждого
  • provide / injectСервис для других плагинов и вклад в поверхность, которой может не оказаться

Плюс то, что ctx даёт, не будучи точкой вклада

  • ctx.config()Свой блок в speq.yaml, уже проверенный по configSchema. Ключ — короткое имя плагина
  • ctx.hostРаботающая сессия: root, reportDir, env, discover(), validate(), run(), runs(), replay()
  • ctx.onEventПодписка на поток событий прогона

Как выглядит минимальный плагин целиком

import { definePlugin } from '@speqkit/plugin-api'

export default definePlugin({
  name: 'speqkit-plugin-kafka',

  // Блок этого плагина в speq.yaml, под ключом `kafka`.
  configSchema: {
    type: 'object',
    properties: { brokers: { type: 'array' } }
  },

  setup(ctx) {
    ctx.defineStepType('kafka.publish', {
      schema: {
        type: 'object',
        properties: { topic: { type: 'string' }, message: {} },
        required: ['topic'],
        additionalProperties: false
      },

      validate(step) {
        return String(step.topic).trim() === ''
          ? [{ path: 'topic', message: "'topic' is empty" }]
          : []
      },

      async execute(exec, input) {
        const producer = await exec.resource('kafka.producer')
        const { offset } = await producer.send(input)
        return { offset }        // → ${publish.offset}
      }
    })
  }
})

Тесты плагина: настоящее ядро, без фейков

@speqkit/test-kit собирает реальные Registry, Executor и раннер — те же, что у speq run. Мок ExecContext был бы второй реализацией контракта, написанной нами и расходящейся с первой, и доказывал бы он только то, что плагин согласен с нашим моком.

const kit = await harness(plugin, { config: { kafka: { brokers: [] } } })

const step = await kit.step({ type: 'kafka.publish', topic: 'orders' })
expect(step.result.offset).toBe(0)

// и диагностики, которые выдал бы плохой тест
expect(kit.validate([{ name: 't', source: 'a.yaml',
  steps: [{ type: 'kafka.publish', topic: '  ' }] }]))
  .toEqual([{ file: 'a.yaml', path: 'steps[0].topic', message: "'topic' is empty" }])

await kit.close()

Кит добавляет к ядру ровно две вещи, которых у автора плагина иначе нет: корень проекта на диске и стек скоупов, удерживаемый открытым между вызовами, — чтобы ${id.поле} работало так же, как в файле теста. Зелёный тест здесь означает, что плагин работает в проекте.

Отладка на живом проекте

cd ../my-service/.speq
speq link ../../speqkit-plugin-kafka   # выигрывает у стора и node_modules
speq plugins                           # что загружено и что дало
speq run --test suites/orders.yaml
speq unlink speqkit-plugin-kafka

Публикация

npm publish                 # --access public для скоупа

После этого плагин ставится как любой другой — speq add speqkit-plugin-kafka. Короткое имя вроде kafka сначала проверяется как @speqkit/plugin-kafka, но пакет, названный полностью, ставится как написан. Ничьё разрешение для этого не нужно.

Совместимость

Плагин и ядро договариваются об одном: мажоре @speqkit/plugin-api. Пока он равен 1, плагин, собранный сегодня, загрузится в ядро, вышедшее позже. Добавление в контракт — минорная версия, изменение или удаление — мажорная; до 1.0 контракт может меняться, и в README пакета это сказано прямо.

Документ описывает speqkit 0.2.0 и контракт @speqkit/plugin-api 0.5.0 (PLUGIN_API_VERSION = 1), состояние на 29 августа 2026 года. Каждая стадия названа файлом, в котором она живёт, — код можно читать рядом. Архитектурные решения и их причины разобраны отдельно, в документе «Плагинный фреймворк speqkit».
