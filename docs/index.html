mostly plugins.

The kernel loads plugins and gets out of the way. HTTP, the CLI, the authoring format, control flow, the reporters — every one of them is a plugin, including the ones that ship in the box. Something you need that we did not build, you write and publish; nothing needs to be agreed with us first.

Quick start

From nothing to a green run

Four commands, and none of them assume your repository is a JavaScript project. The most common reason to reach for speq is a Go or Python service whose team does not want a node_modules in it.

  1. 1

    Install

    Pick whichever is already true of the machine. All three land the same speq.

    # macOS and Linux, no toolchain required — the archive carries its own Node
brew install speqkit/tap/speqkit

# or, the same binary without Homebrew
curl -fsSL https://speqkit.github.io/speqkit/install.sh | sh

# or, if Node is already there
npm i -g speqkit

    Why a binary at all. speq install already speaks the registry protocol itself and never shells out to a package manager — but that still left Node underneath it. The released archives have the runtime inside, so a repository with no JavaScript in it stays that way.

  2. 2

    Scaffold

    cd my-service
speq init

    Writes .speq/ and nothing else. The plugins themselves live in ~/.speq, shared by every project on the machine, so what lands in your repository is a config file and a lock file. 

    # .speq/speq.yaml
version: 1

plugins:
  - yaml          # the authoring format is itself a plugin
  - http
  - assert
  - data
  - cli
  - junit

http:
  baseUrl: http://localhost:8080
  3. 3

    Write a test

    # .speq/suites/menu.yaml
id: menu.reads
title: the menu comes back with categories
tags: [smoke]

steps:
  - id: menu
    type: http
    method: GET
    url: /menu
    assert:
      - type: status
        expected: 200
      - type: length
        path: body.categories
        at_least: 1

    The whole language is one page →

  4. 4

    Install the plugins, and run

    speq install       # resolves, verifies, stores, writes speq.lock
speq validate      # catches typos and bad schemas — no network, milliseconds
speq run           # the suites

    The exit code comes from the spine. 0 passed, 1 failed, 2 the configuration was wrong before anything ran. A misspelled --reporter or a missing ${env:VAR} is caught before the first test, not twenty minutes into the suite.

In CI

- run: speq install --frozen                     # exactly the lock, or fail
- run: speq run --env ci --reporter console,junit
- uses: actions/upload-artifact@v7
  if: always()
  with: { name: speq-report, path: .speq/reports/ }

--frozen fails when speq.lock has drifted from speq.yaml. A plugin that came from a git ref was pinned to a commit at install time, so CI installs what was reviewed rather than wherever the tag has moved since.

The kernel

What is in the middle, and what deliberately is not

packages/core is a loader and a test model. It contains no protocol, no command, no report format and no control construct — not because those are unimportant, but because each of them is a decision that belongs to whoever is writing the tests, and a decision baked into a kernel is a decision nobody can take back.

It owns

  • Plugin registry and lifecycle
  • Config, with extends and environment layers
  • The test model: Suite → Test → Step → Assertion
  • Execution, ${…} resolution, and the re-entrant runSteps
  • Resources scoped to run | suite | test
  • The event bus
  • Results, artifacts and the run log
  • Validation

It does not own

  • HTTP — @speqkit/plugin-http
  • The terminal — @speqkit/plugin-cli
  • YAML, and the file format at all — @speqkit/plugin-yaml
  • loop and retry — @speqkit/plugin-loop
  • The assertion vocabulary — @speqkit/plugin-assert
  • Where a value comes from — @speqkit/plugin-data
  • JUnit XML and summary.json — two reporter plugins
  • Browsers — @speqkit/plugin-playwright
The line

Something moves into the kernel when a plugin cannot express it without breaking an invariant. That rule has been applied three times and refused many more: setup and cleanup went in because a plugin cannot write finally without leaking its child scope back into the caller. use — the most common step in a real suite — stayed a plugin, because re-entrancy already expressed it completely.

Eight contribution points, and no ninth

A plugin is a module that exports a manifest and gets a context. Everything it can add to the framework is on this list, and the list stays this length: eight points are eight contracts held forever, and the pressure to open a ninth for annotations was refused on exactly those grounds.

  • defineStepTypea new kind of step, with a schema so a bad one fails before the run
  • defineAssertionTypea new word in the vocabulary a test says what it means in
  • defineValueProvidera new answer to ${something:…}
  • defineReportera new thing to build out of the event stream — the console output is one of these
  • defineResourcesomething opened once per run, suite or test, and torn down in reverse
  • defineLoadera new authoring format; YAML is not privileged
  • defineCommanda verb, offered to whichever surface is listening
  • defineServicesomething other plugins may use, and must stay usable without

ctx.inject(['cli'], …) rather than a plain lookup, so a plugin that contributes a command is perfectly usable in an editor where no terminal surface exists at all: the callback simply never fires.

The invariants

Twelve things that are true, and a test that fails if one stops being

Pinned by packages/core/test/kernel.test.ts, gate.test.ts and reporting.test.ts. If one starts failing, the spine moved and the fix belongs in the kernel — not in the test.

  • A step type the kernel has never heard of runs, contributed at load time.
  • A plugin nests steps through ctx.runSteps in a child variable scope, and that scope does not leak back to the parent.
  • Resources open once per scope and tear down in reverse order.
  • A plugin contributes to a surface that may not be loaded, and stays usable when nobody provides it.
  • Two plugins cannot claim the same step type.
  • A plugin built against a different plugin-api major is refused at load.
  • A crash inside a plugin is error, never failed.
  • All three resource scopes are real: run outlives the suite, suite outlives the test, and the outer ones tear down even when a test blows up.
  • Bytes handed to attach come back out of the run byte-for-byte, and every reporter is told where they went.
  • A plugin installed from a registry loads out of the store, with its own dependencies resolvable, and --frozen reproduces it without a network.
  • An environment layers settings and cannot add a plugin, so the lock stays true whichever environment runs.
  • The event stream alone is enough to build a report: replaying a recorded run produces a byte-identical file to watching it live.

The last one is load-bearing. It is why speq report can re-render a finished run without re-running it, and it is the reason no reporter is given a back door to the run's result object: a report that cannot be built from events alone is a hole in the events.

What ships

Fifteen packages, eleven of them plugins

Every plugin-* depends on @speqkit/plugin-api and on nothing else of ours — never on the kernel. A plugin runs inside a kernel and reaches it as ctx.host; one that imports speqkit instead ships a second kernel that the installer will faithfully store and the plugin will faithfully boot. A test fails if any manifest here ever names it.

@speqkit/plugin-apiThe public contract. Types only. Its major version is the compatibility boundary.
speqkitThe kernel and the speq bootstrap. Unscoped, because it is what you install.
@speqkit/installerResolve, verify, store, lock. No npm CLI involved.
@speqkit/plugin-yamlThe default authoring format, and speq migrate — proof the format is a plugin.
@speqkit/plugin-httpHTTP steps, multipart, retries, and the two checks that are actually about HTTP.
@speqkit/plugin-assertThe vocabulary: equality, order, membership, text, presence, size, shape, JSON Schema.
@speqkit/plugin-useComposition: shared blocks, module actions and fixtures, all through one use.

@speqkit/plugin-cliThe terminal surface. Publishes the cli service; the console output is a reporter.

Delivery

How any of this reaches a machine

Nobody cuts a release here. A version bump in a package.json is the whole gesture: merge it to main, and if the gate is green the version is on npm — and if the kernel's version moved, four executables, a GitHub release and the Homebrew formula follow it.

How speqkit ships

One workflow, five jobs, two questions asked of the outside world rather than of the repository: what is missing from the registry, and what has no tag. That is what makes a half-finished release safe to simply re-run.

How your plugin ships

Writing a plugin

npm create speqkit-plugin kafka
cd speqkit-plugin-kafka && npm install && npm test

The scaffold makes the decisions that are easy to get wrong: the contract is a peer, nothing depends on the kernel, the step type and the assertion carry schemas, the speqkit-plugin keyword is there so the package can be found, and the release workflow is already wired. Its tests use @speqkit/test-kit, which assembles the real Registry, Executor and runner — there are no fakes to drift, and green means it works in a project.

Taking part

A plugin is published from your own repository and needs nothing from us — that is the whole architecture, not a courtesy. Everything else lives in the repository: CONTRIBUTING for the setup, the gate you can run locally and the two things about the contract that are deliberately closed; the changelog for what each release contained; the security policy for what to do instead of opening an issue; and the code of conduct, which everyone taking part follows.
