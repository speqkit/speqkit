Releasing

A version bump in a package.json is the whole gesture. Merge it to main and, if the gate is green, that version is on npm — and if the kernel's version moved, four executables, a GitHub release and the Homebrew formula follow it. The same machinery is offered to anyone publishing a plugin of their own.

The idea

The version in the manifest is the intent

There is no changelog tool here, no commit-message convention and no "cut a release" button. The version written in a package.json is the decision: it arrives in a diff, gets reviewed like anything else, and one person can see the whole thing at once. Everything downstream is derived from it.

What shipsDecided by
an npm packageits version is not in the registry yet
a tag, four binaries, the tappackages/core's version has no tag on the remote
Why both questions face outward

Neither is asked of the repository. The npm registry says which versions exist and the git tags on the remote say which releases were cut — which is what makes the whole thing idempotent. Re-running a job that already succeeded finds nothing to do. A job that died between package four and package five can simply be re-run, because what got through the first time is now indistinguishable from something published last month.

You can ask for the answer before pushing anything: 

node scripts/release-plan.mjs

release plan for v0.2.0

  publish to npm
    speqkit@0.2.0
    @speqkit/plugin-api@0.9.0
    @speqkit/plugin-assert@0.1.0
    …

  cut v0.2.0: four executables, a GitHub release and the Homebrew formula
How speqkit ships

Five jobs, and the gate is the real one

  1. 1

    plan

    Runs scripts/release-plan.mjs, writes its answer into the job summary and hands it to everything below. If the answer is "nothing", the rest of the workflow does not run.

  2. 2

    gate

    uses: ./.github/workflows/ci.yml — literally the CI file, not a copy of its steps. Typecheck and build and the full test suite on Node 20, 22 and 24; then scripts/verify-publish.mjs, which packs the real tarballs, serves them from a throwaway registry over HTTP, installs them into a throwaway store and runs the CLI out of dist under plain node; then the standalone binary, verified again with PATH emptied.

    Why the same file and not a copy. The battery that decides whether a commit ships has to be the one a pull request faces, or the two drift — and the release one is the copy nobody reads until it is too late.

  3. 3

    npm

    pnpm -r publish --access public --no-git-checks --provenance

    Walks the workspace in dependency order, turns every workspace:* into the version it resolved to, and skips whatever the registry already has — the same rule the plan reported, asked of the same place. --provenance records which workflow at which commit built each tarball, and anyone can check it.

  4. 4

    binaries

    Four native runners: macos-15, macos-15-intel, ubuntu-24.04, ubuntu-24.04-arm. Each downloads the pinned Node from nodejs.org, checks it against SHASUMS256.txt, injects the bundled kernel as a SEA blob — and then runs the result: installs plugins from a throwaway registry and executes a suite with no Node on PATH at all, and finally installs itself through install.sh.

    Not cross-compiled, and it cannot be. The SEA blob carries a V8 code cache valid only for the exact runtime it goes into, and only macOS can re-sign a Mach-O after injection.

  5. 5

    release, then tap

    Renders the Homebrew formula from the checksums of the artefacts themselves — refusing outright if any of the four platforms is missing — creates the tag and the GitHub release, uploads everything, and pushes Formula/speqkit.rb into speqkit/homebrew-tap.

    A tap that is right for three platforms is worse than no tap: brew install would work for the maintainer and fail for whoever bought the other laptop.

Safety rails

The whole workflow is skipped unless github.repository == 'speqkit/speqkit', so a fork pushing to its own main cannot publish ours. Concurrency is cancel-in-progress: false: the CI of a superseded commit is worth nothing, but a publish interrupted halfway leaves the registry in a state no later run can explain. And the tag is created from packages/core's version, so the two cannot disagree.

Setup

Two secrets, set once

SecretWhat it is
NPM_TOKEN An npm automation token for the speqkit org. Automation rather than publish, because a publish token prompts for a second factor and a CI runner has no thumbs.
HOMEBREW_TAP_TOKEN A fine-grained PAT with contents: write on speqkit/homebrew-tap. The default GITHUB_TOKEN cannot reach another repository, which is the correct default and the reason this one exists.

The tap repository itself is created once and then never touched by hand: 

gh repo create speqkit/homebrew-tap --public \
  --description "Homebrew formulae for speqkit"

To exercise everything without publishing anything — useful for finding out that a runner label changed underneath us on a day that is not release day: 

gh workflow run release.yml -f dry_run=true
Your plugin

Six lines, one token

A plugin whose release is something its author does by hand is a plugin that gets its fix on the day its author has an afternoon. That is the failure mode an ecosystem cannot afford, because that fix is nobody else's to ship — so the machinery above is offered as a reusable workflow you call from your own repository. 

# .github/workflows/release.yml, in your plugin's repository
name: release

on:
  push:
    branches: [main]

jobs:
  release:
    uses: speqkit/speqkit/.github/workflows/plugin-release.yml@main
    secrets:
      NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

That is the whole integration. It installs, builds, runs your tests against the real kernel, checks that the package would actually load once installed, and publishes with provenance — and does nothing at all when that version is already in the registry, so an ordinary commit is not a release.

Scaffolded plugins already have it

npm create speqkit-plugin kafka writes that file for you, along with publishConfig.access: public in the manifest — npm defaults a scoped package to restricted, and the failure is a plugin that publishes successfully and 404s for everyone who tries to install it.

The one secret

  1. On npmjs.com: Access Tokens → Generate → Automation.
  2. In your repository: Settings → Secrets and variables → Actions → New repository secret, named NPM_TOKEN.

By hand

The release you do from a terminal

For the first one, for a plugin in a repository with no CI, or for the afternoon you need a version out and the runners are queued. It runs the same three questions in the same order, and stops before publishing if any of them fails. 

export NPM_TOKEN=npm_xxxxxxxx     # or just 'npm login' once
curl -fsSL https://speqkit.github.io/speqkit/release-plugin.sh | sh

# see what it would do, and publish nothing
curl -fsSL https://speqkit.github.io/speqkit/release-plugin.sh | sh -s -- --dry-run

# a plugin inside a monorepo
./release-plugin.sh --dir packages/my-plugin
speqkit-plugin-kafka 0.2.0
  /home/mira/speqkit-plugin-kafka

1/4  build and test
2/4  would this install and load?
  ok    keyword `speqkit-plugin`
  ok    `@speqkit/plugin-api` is a peer
  ok    does not carry a second kernel
  ok    `./dist/index.js` is built and packed
3/4  is 0.2.0 already out?
  no — 0.2.0 is new
4/4  publish

published speqkit-plugin-kafka@0.2.0

The token never touches a file the script keeps. With NPM_TOKEN set it is handed to npm through a temporary config that names the environment variable rather than the value, removed when the script exits. Without it, the script falls back to whatever npm whoami already has — and it will never prompt, because a script that blocks on a one-time password is a script that hangs in a pipe at 2am.

The check

Would this actually install and load?

Both paths run the same script, and you can run it yourself against any directory holding a plugin's package.json: 

node check-plugin-package.mjs [dir] [--json] [--offline]

Every question in it is a bug this project shipped, or caught one commit before shipping:

  • exports → .tsGreen locally, because the tests resolve src through a bundler alias — and unloadable once installed, because Node refuses to strip types inside node_modules.
  • dist not in filesnpm packs the manifest, not the directory. The tarball is a README and a promise.
  • the kernel as a dependencyThe installer will faithfully put a second copy of speqkit in the store and the plugin will faithfully boot it — and the compatibility check then compares a contract against itself.
  • plugin-api not a peerSame failure, from the other end: the contract has to come from the kernel the user installed.
  • no speqkit-plugin keywordThe plugin works and nobody finds it.
  • a scoped name in @speqkitA scope you cannot publish into, found now rather than at the publish.

It is fetched rather than vendored, so a plugin generated last year gains new checks without its author editing a file they have never read. Exit codes: 0 all clear, 1 something is wrong, 2 there is nothing to check.

When nothing happens

The workflow ran and published nothing

That is almost always correct. In order of likelihood:

What you seeWhat it means
"Nothing to publish" That version is already in the registry. Publishing is not how you change what is there — bump the version.
The gate is red Nothing downstream ran, by design. Fix the test, push again; the plan is recomputed from scratch.
npm published, no tag A plugin's version moved and the kernel's did not. A patch to one plugin does not deserve four 100 MB executables that would be byte-identical.
The job failed partway through publishing Re-run it. What went out the first time is skipped, because the registry is the source of truth and it now says so.
Nothing at all, on a fork github.repository is checked before anything else runs.
